# Ранбук: выкат на doctor

Право мерджа не есть право деплоя — так было написано в ТЗ §14.2а, и до
2026-09-11 выкат оставался владельцу. С 2026-09-11 он передан агенту (ответ на
мешок М5 п.1 в `docs/PLAN-to-done.md`), и этот ранбук — то, что исполняется
вместо владельца.

Ни один cron на doctor не делает `git pull`. Checkout там обновляется только
этим ранбуком.

**Гейт Г4 живой.** Он не про отдельную команду миграции — миграции реестра в
этом проекте живут внутри `mara_ingest.connect()` и выполняются при каждом
открытии базы. Значит выкат кода **и есть** выкат миграции, и шаг 2 проверяет
это первым делом, до всего остального.

## 0. Почему нельзя просто `git pull`

Checkout на doctor годами стоял на ветке выката с локальными коммитами:
кто-то правил код на месте, а потом ту же работу вливали в `main` через PR.
`git pull` на такой ветке даёт merge-коммит и расхождение, которое потом
никто не разберёт. Поэтому выкат — это `reset --hard` на приколоченный sha, а
локальные коммиты перед этим **доказываются избыточными**, а не осматриваются
на глаз.

## 1. Что имеем до выката

```bash
ssh doctor 'cd ~/mara-second-brain
  git branch --show-current
  git rev-parse HEAD
  git status --porcelain
  git fetch -q origin
  git rev-list --count HEAD..origin/main      # насколько отстали
  git log --oneline origin/main..HEAD'        # чем разошлись
```

Записать в протокол полный HEAD (не `--short`): он понадобится на шаге 2 и в
откате.

**Остановиться, если `git status --porcelain` выдал что-нибудь, кроме заведомо
генерируемого.** `reset --hard` затирает незакоммиченные правки в
отслеживаемых файлах, и тег их не спасает: тег держит коммит, а не рабочее
дерево. Раздел 0 прямо говорит, что на месте тут правили, — значит это не
гипотеза. Если правки есть, а разбираться некогда:

```bash
ssh doctor 'cd ~/mara-second-brain && git diff > ~/deploy-dirty-$(date +%s).patch && wc -c ~/deploy-dirty-*.patch'
```

Прогон 2026-09-11: ветка `deploy/codex-usage-20260909`, HEAD `54f8464`,
отставание **53 коммита**, два локальных коммита, `git status --porcelain` —
только `config/r2-filters.txt.md5` (генерируемый, не отслеживается).

## 2. Приколотить целевой sha и узнать, что он несёт

Между доказательством избыточности и `reset` `main` может уехать, и выкатится
не то, что доказывали. Поэтому сначала — sha, и дальше весь выкат только
против него.

```bash
ssh doctor 'cd ~/mara-second-brain
  git rev-parse origin/main
  git log --name-only --no-renames --pretty=format: origin/main..HEAD | sort -u | sed "/^$/d"'
```

**Выписать sha в протокол и дальше подставлять его буквально, вместе с
кавычками.** Переменной shell тут не обойтись: каждый шаг — своя сессия `ssh`,
и `sha=` из этой команды в следующей уже не существует.

Кавычки вокруг дырок — не оформление, а единственная защита от незаполненной
дырки. Проверено (круг 2 ревью PR #88):

| если дырку не заполнить | без кавычек | в кавычках |
|---|---|---|
| `git reset --hard` | `rc=0`, сброс на **локальный** `main`, незакоммиченное затёрто, протокол зелёный | `fatal: ambiguous argument ''`, `rc=128` |
| `git diff --quiet … HEAD -- <пути>` | `rc=0` на чистом дереве — «избыточность доказана» из ничего | `fatal: bad revision ''`, `rc=128` |
| `git diff <старый HEAD> … -- scripts/` | пусто — «миграции нет», прямо мимо Г4 | `rc=128` |

`rc=128` этот ранбук трактует верно уже ниже («команда сломалась, читать текст
ошибки»), так что кавычек достаточно. Без них незаполненная дырка даёт не
ошибку, а **зелёный протокол над невыкаченным деревом**.

**Два исключения, где кавычек мало.** Проверка миграции в конце этого шага
отдаёт `git` в конвейер, и `rc` там принадлежит `grep`, а не `git` — поэтому в
ней стоит отдельный `echo "git rc=$?" >&2`. Шаг 5 достаёт путь из `ExecStart`, и
пустая переменная там не ломает `git -C` вовсе — поэтому там `exit 1`, а не
`echo rc=$?`. Оба места отмечены на месте.

Второй вывод — **список путей, которые трогают локальные коммиты**, полученный
командой, а не набранный руками. Он идёт в протокол: список из головы нельзя
проверить, а опечатку в пути `git diff` не заметит (`git diff --stat A B --
нет/такого/пути` даёт пустой вывод и `rc=0` — то есть «пусто» одинаково
читается и как «совпало», и как «я промахнулся»).

Доказательство избыточности — числом, не пустотой:

```bash
ssh doctor 'cd ~/mara-second-brain
  git diff --quiet "<sha>" HEAD -- <пути из предыдущей команды>; echo rc=$?'
```

`rc=0` — расхождений нет, работа локальных коммитов уже в `main`. `rc=1` —
**остановиться**: это незалитая работа, её оформляют PR-ом, а не затирают.
`rc=128` — команда сломалась, читать текст ошибки.

Проверить, что целевой коммит зелёный (`enforce_admins` включён с 2026-09-11,
но красный коммит мог попасть в `main` и до этого):

```bash
gh run list --commit "<sha>" --limit 5
```

**Что несёт диапазон по схеме реестра:**

```bash
ssh doctor 'cd ~/mara-second-brain && git diff "<старый HEAD>" "<sha>" -- scripts/; echo "git rc=$?" >&2' \
  | grep -inE '^[+-].*(def connect|_ужать_ledger|alter table|create table|rename to|drop table|drop column|user_version|ЛЕДЖЕР)'
```

`echo "git rc=$?" >&2` здесь обязателен, и это исключение из таблицы выше.
Конвейер отдаёт код **последней** команды, то есть `grep`, а `grep` без
совпадений даёт `1` — тот же `1`, что и при «диапазон чист». Сломанный `git` от
пустой дырки съедается конвейером целиком: `git diff "" "" -- scripts/ | grep …`
и `git diff HEAD HEAD -- scripts/ | grep …` дают одинаковый пустой stdout и
одинаковый `rc=1`, отличаясь только текстом на stderr. Это **единственная точка
решения Г4 в документе**, и снимать её с пустоты stdout нельзя. Нашёл круг 3.

`grep -inE`, а не `-nE`: расширение шаблона обосновано будущим кодом, а будущий
код может написать `CREATE TABLE` и `PRAGMA user_version` заглавными. Сегодня
все 19 совпадений в `scripts/*.py` — в нижнем регистре, `-i` бесплатен.

Смотрим весь `scripts/`, а не только `mara_ingest.py`, и шаблон шире имён из
сегодняшнего кода: помощник миграции, дописанный в тело `connect()`, не изменит
строку `def connect` и без `alter table` прошёл бы мимо. На реальном диапазоне
узкая версия срабатывала (13 совпадений на `e55dfc8~1..dca824f`), но
срабатывать она должна не только на уже известной миграции.

Непустой вывод значит, что выкат несёт миграцию реестра, и дальше идти
**только через гейт Г4**: свежая резервная копия с известным путём и sha,
пройденное учение восстановления (Т3б.1), явное разрешение владельца. Не
«вроде там ничего страшного», а три условия.

Прогон 2026-09-11: пусто (проверено `git diff --stat origin/main HEAD --`
по списку из пяти путей; работа ушла в `main` как PR #83 и #84). **А вот
проверки на миграцию в тот прогон не было, и она бы сработала:** диапазон
нёс `e55dfc8` (PR #79), где `_ужать_ledger()` перестраивает `commitments`,
`conversations` и `projections` целиком (`rename to *_old` → `create table` →
`insert select` → `drop table`), и делает это из `connect()`, то есть при
первом же открытии базы — кроном или рестартом демона. Гейт Г4 был пройден
мимо, не заметив. Постфактум: во всех трёх таблицах **0 строк**
(`select count(*)`), `*_old` не осталось, терять было нечего — но узнал я это
после, а не до. Отсюда и этот шаг.

## 3. Точка возврата и выкат

Тег дешевле сожалений: он держит старый HEAD достижимым после `reset`. Имя с
временем, а не только с датой: повтор в тот же день иначе падает на «tag
already exists» с `rc=128`, и под `&&` **вся цепочка встаёт** — выкат
прерывается на первом же шаге, а оператор читает про тег и ищет беду в
`reset`. Проверено: `git tag <существующий> HEAD && echo …` → `rc=128`, `echo`
не выполняется.

Имя тега печатается в протокол отдельной командой: `git tag` на успехе молчит,
а откатываться потом надо по имени.

Команды сцеплены `&&` нарочно. Без сцепки упавший `git checkout main`
(незакоммиченное перекрыло переключение) не помешает `git reset --hard`
отработать **на ветке выката** и сдвинуть её на `main`.

Демон гасится до сброса и поднимается после шага 4. Иначе между сбросом и
рестартом на одной базе работают два поколения кода: кроновый процесс откроет
базу уже **новым** кодом под ещё **старым** демоном — и миграцию из шага 2
выполнит он.

Кто именно открывает реестр (по `grep -l "mi.connect("` против
`install/mara.cron`, а не по памяти): `contextd_reconcile.py` в :07 каждого
часа и в 8:00, `core-backup.py` в 4:10, `blob_retention.py` в 4:40.
`context_pack.py` импортирует `mara_ingest`, но `connect()` не зовёт;
`codex-usage.py` к базе не ходит вовсе (`grep -c "sqlite\|mara_ingest"` → 0),
хотя первая редакция этого ранбука называла именно его.

Из этого списка важнее всех 4:10: это **бэкап**. Выкат с миграцией, сделанный
в полночь, к утру получит перестройку руками того самого прогона, который Г4
требует как предусловие, — и копию уже после неё.

```bash
ssh doctor 'sudo systemctl stop contextd'
ssh doctor 'cd ~/mara-second-brain
  t=deploy-before-$(date +%Y%m%d-%H%M%S) \
    && git tag "$t" "$(git rev-parse HEAD)" \
    && echo "тег: $t" \
    && git checkout main -q \
    && git reset --hard "<sha>" \
    && git rev-parse HEAD && date -Is'
```

**Напечатанный HEAD обязан совпасть с `<sha>`.** Не совпал — стоп, дальше не
идти: это и есть тот случай, когда дырку не заполнили, а `&&`-цепочка всё равно
дошла до конца. Сверять глазами тут дёшево, потому что оба числа в одном
выводе.

Время шага записать в протокол: без него из записи не выводится даже то, что
рестарт был после сброса.

Прогон 2026-09-11: тег `deploy-before-20260911` на `54f8464`, HEAD стал
`dca824f`. Демон в тот прогон **не гасился**, и окно смешанного кода
восстанавливается числом: `git reflog --date=iso` даёт сброс в
`04:19:15 +0300`, `systemctl show contextd -p ActiveEnterTimestamp --value` —
`Fri 2026-09-11 04:19:26 MSK`. **11 секунд**, не «около минуты». В это окно из
крона не попадал никто (в :19 идёт только `codex-usage.py`, а он к базе не
ходит), поэтому перестройку таблиц выполнил рестарт демона.

Тот же reflog говорит `reset: moving to origin/main`: прогон сбрасывался на
**ветку**, а не на приколоченный sha. Дисциплину из шага 2 сам прогон не
проходил — как и гашение демона.

**Откат.** `git reset --hard deploy-before-<метка>` возвращает **код**.
Перестроенные таблицы реестра он не возвращает: старый код на ужатых
таблицах получит `IntegrityError` там, где раньше писал NULL. Если шаг 2
показал миграцию — откат означает ещё и восстановление базы из той самой
резервной копии, путь и sha которой записаны до сброса.

Тег и ветка выката живут только на doctor: `git cat-file -t 54f8464` в
репозитории отвечает `fatal: Not a valid object name`. Пропадёт диск —
пропадёт и точка возврата. Пушить тег в публичный репозиторий стоит только
после шага 2: `rc=0` там и означает, что в этих коммитах нет ничего, чего нет
в `main`.

## 4. Крон

`install/mara.cron` — единственный источник правды. Руками `crontab -e` не
править никогда: правка переживёт до первого `--apply` и исчезнет.

```bash
ssh doctor 'cd ~/mara-second-brain && bash install/install-cron.sh --check'
# расхождение → bash install/install-cron.sh --apply
```

Пара `sudo systemctl stop`/`start` из шагов 3 и 6 в прогоне 2026-09-11 не
исполнялась (демон не гасился). Риск низкий и проверен: `ssh -o
BatchMode=yes doctor 'sudo -n true'` → `rc=0`, tty для sudo здесь не нужен.

`rc=0` доказывает все три условия сразу (`install/install-cron.sh`
заканчивается `exit $drift`, а `drift=1` даёт и побитый маркер, и расхождение
блока, и строки мимо блока). Порядок «сброс → `--check`» важен: сверяется уже
новый `install/mara.cron`.

Прогон 2026-09-11: «блок в crontab совпадает с install/mara.cron», rc=0 —
`--apply` не понадобился.

## 5. Проверить дерево до подъёма демона

Сломанное дерево лучше обнаружить, пока демон ещё лежит.

```bash
ssh doctor 'cd ~/mara-second-brain
  d=$(systemctl cat contextd | sed -n "s#^ExecStart=[^ ]* \(.*\)/scripts/contextd\.py.*#\1#p")
  [ -n "$d" ] || { echo "путь из ExecStart не извлёкся — СТОП"; exit 1; }
  [ "$(realpath "$d")" = "$(realpath ~/mara-second-brain)" ] || { echo "юнит смотрит не в этот checkout — СТОП"; exit 1; }
  echo "юнит смотрит в этот checkout"
  git -C "$d" rev-parse HEAD
  python3 -c "import sys; sys.path.insert(0,\"$d/scripts\")
import contextd, mara_ingest, contextd_reconcile
print(\"импорт ок\", sys.version.split()[0])"'
```

Три `exit 1` вместо трёх `echo rc=$?` — не стиль, а необходимость. `git -C ""
rev-parse HEAD` **не ошибка**: пустой `-C` это no-op, git остаётся в текущем
каталоге и печатает HEAD того дерева, куда сделан `cd`, то есть ровно то число,
которое строка ниже требует сверить с `<sha>`. Проверено: `git -C "" rev-parse
HEAD` → `rc=0` и валидный sha. Единственный вероятный отказ `sed` — пустой
вывод, и он же единственный, которого `git -C` не замечает. Нашёл круг 3 ревью
PR #88: правка круга 2 закрыла «зелёное число над невыкаченным деревом» в
`reset` и завела его же в доказательстве нового кода.

`sys.path` тоже берёт `$d`, а не `scripts` от текущего каталога: разойдись
пути — импорт проверял бы не то дерево, чей HEAD только что доказывали.

Первые две строки замыкают связку **числом, а не глазами**: путь берётся из
`ExecStart` самого юнита, сравнивается с checkout, и `git -C` печатает HEAD
именно того дерева, из которого запускается демон. Этот HEAD обязан совпасть с
`<sha>` из шага 3. Прежняя редакция печатала `ExecStart` и `realpath` рядом и
просила увидеть совпадение — то есть просила ровно того осмотра на глаз, от
которого отказывается раздел 0.

Путь наружу не печатается нарочно: в `ExecStart` стоит абсолютный путь с
системным именем пользователя doctor, а репозиторий публичный. Сравнение
отдаёт `rc`, не путь.

Импорт трёх модулей — самая дешёвая проверка того, что дерево хотя бы
синтаксически живо на той версии Python, что стоит на doctor (3.12.3). Он идёт
**отдельным** интерпретатором и `connect()` не вызывает, то есть мимо
единственного, что здесь реально может упасть, — перестройки таблиц из шага 2.
Гейт целиком на doctor не гоняем: он идёт в CI и на BetaPi.

Прогон 2026-09-11: импорт прошёл, но **после** рестарта, а не до; сверки
`ExecStart` с checkout не было. Постфактум она сходится: `rc=0`, HEAD дерева
юнита — `dca824fd2ee806888264cd97bea45f0bbb748816`.

## 6. Поднять сервис

```bash
ssh doctor 'sudo systemctl start contextd'
ssh doctor 'systemctl is-active contextd
  systemctl show contextd -p ActiveEnterTimestamp --value
  curl -s --retry 5 --retry-connrefused --retry-delay 1 \
       -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8788/metrics
  tr "\0" "\n" < /proc/$(systemctl show contextd -p MainPID --value)/cmdline \
    | grep -m1 contextd.py | sed "s#^$HOME#~#"
  journalctl -u contextd -n 12 --no-pager | tail -8'
```

`--retry-connrefused` — не перестраховка: `serve()` зовёт `mi.connect(root)`
(`scripts/contextd.py:1103` на `5fe51de`; на `dca824f` та же строка) **до**
`make_server`, а юнит `Type=simple`
возвращает управление сразу на exec. curl из следующей сессии `ssh` успевает
застать порт закрытым и печатает `000`, что слепой оператор прочтёт как отказ.

Путь скрипта берётся `grep -m1 contextd.py`, а не `sed -n 2p`: второй аргумент
интерпретатора — это скрипт только пока у `python3` нет флагов. Допишут в юнит
`-u`, и вторая строка станет флагом. `MainPID=0` (сервис лежит) отказывает
громко: `/proc/0/cmdline: No such file or directory`.

Путь скрипта из `/proc/<pid>/cmdline` — последнее звено доказательства: живой
процесс запущен из того дерева, чей HEAD напечатал шаг 5. `sed` заменяет
домашний каталог на `~`, чтобы системное имя пользователя не уезжало в
протокол публичного репозитория.

Ждём `active`, отметку времени позже шага 3 и `200`.

`200` получен **с петли**. Про доступ снаружи он не говорит ничего: на doctor
`MARA_BIND=0.0.0.0`, порт виден из локалки, а `/metrics` держат две вещи —
проверка на loopback в `scripts/contextd.py` (без токена пускают только с
петли, остальных — через `authed()`) и роутер. Отдельной командой снаружи это
здесь не проверялось.

Рестарт рвёт заливки в полёте. Телефон повторит сам: 413 у него терминальный,
а обрыв — нет.

Расход **нового** процесса — числом:

```bash
ssh doctor 'systemctl show contextd -p CPUUsageNSec -p MemoryPeak'
```

Прогон 2026-09-11, через час после подъёма: `CPUUsageNSec=1049349000` (1.05 с),
`MemoryPeak=15429632` (14.7 МБ). На doctor `systemd 255 (255.4-1ubuntu8.17)`;
`MemoryPeak` появился в systemd 254, и на более старой машине его в выводе
просто не будет — это не ошибка выката.

Расход **старого** процесса живёт в другом месте: systemd пишет его в журнал
одной строкой в момент остановки, и `systemctl show` его уже не покажет.

```bash
ssh doctor 'journalctl -u contextd --no-pager | grep -E "Consumed .*CPU" | tail -3'
```
