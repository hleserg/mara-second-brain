# Ранбук: выкат на doctor

Право мерджа не есть право деплоя — так было написано в ТЗ §14.2а, и до
2026-09-11 выкат оставался владельцу. С 2026-09-11 он передан агенту (ответ на
мешок М5 п.1 в `docs/PLAN-to-done.md`), и этот ранбук — то, что исполняется
вместо владельца.

Ни один cron на doctor не делает `git pull`. Checkout там обновляется только
этим ранбуком.

**Гейт Г4 живой.** Он не про отдельную команду миграции — миграции реестра в
этом проекте живут внутри `mara_ingest.connect()`. **Проверка** схемы идёт при
каждом открытии базы, **перестройка** — один раз: `_ужать_ledger()` возвращает
управление сразу, как только все ключи `ЛЕДЖЕР` уже `not null`.
Первая редакция этого абзаца говорила «выполняются при каждом открытии» — фраза
была списана из комментария об **аддитивных** миграциях в `connect()` вместе со
словом «идемпотентно», но без квалификатора, и противоречила строке ниже в этом
же документе («при первом же открытии базы»).

Ссылки здесь и дальше — на имена функций, а не на номера строк. Номер строки
верен ровно про то дерево, на котором посчитан (правило 20), и гниёт с первым
же коммитом; прежняя редакция этого абзаца звала `scripts/mara_ingest.py:161`,
а там стоит сама застава `if all(_обязателен(...))` — `return` строкой ниже.
Имя функции переживает правку, номер — нет. Значит выкат кода **и есть** выкат миграции, и шаг 2 проверяет
это первым делом, до всего остального.

## 0. Почему нельзя просто `git pull`

Checkout на doctor годами стоял на ветке выката с локальными коммитами:
кто-то правил код на месте, а потом ту же работу вливали в `main` через PR.
`git pull` на такой ветке даёт merge-коммит и расхождение, которое потом
никто не разберёт. Поэтому выкат — это `reset --hard` на приколоченный sha, а
локальные коммиты перед этим **доказываются избыточными**, а не осматриваются
на глаз.

## 1. Что имеем до выката

```bash
ssh doctor 'cd ~/mara-second-brain
  git branch --show-current
  git rev-parse HEAD
  git status --porcelain
  git fetch -q origin
  git rev-list --count HEAD..origin/main      # насколько отстали
  git log --oneline origin/main..HEAD         # чем разошлись
  git branch -v --no-merged origin/main'     # чем разошлись ветки в стороне
```

Записать в протокол полный HEAD (не `--short`): он понадобится на шаге 2 и в
откате.

Последняя команда — не любопытство: шаг 2 решает судьбу блока доказательства
избыточности по **обоим** выводам, и без неё шаг 2 ссылается на то, чего никто
не получал. Круг 1 ревью PR #103 поймал ровно это: прогон 2 объявил блок
пропущенным «по правилу шага», а `--no-merged` на машине был непуст.

**Остановиться, если `git status --porcelain` выдал что-нибудь, кроме заведомо
генерируемого.** `reset --hard` затирает незакоммиченные правки в
отслеживаемых файлах, и тег их не спасает: тег держит коммит, а не рабочее
дерево. Раздел 0 прямо говорит, что на месте тут правили, — значит это не
гипотеза. Если правки есть, а разбираться некогда:

```bash
ssh doctor 'cd ~/mara-second-brain && git diff > ~/deploy-dirty-$(date +%s).patch && wc -c ~/deploy-dirty-*.patch'
```

Прогон 1 (2026-09-11 04:19): ветка `deploy/codex-usage-20260909`, HEAD `54f8464`,
отставание **53 коммита**, два локальных коммита, `git status --porcelain` —
только `config/r2-filters.txt.md5` (генерируемый, не отслеживается).

## 2. Приколотить целевой sha и узнать, что он несёт

Между доказательством избыточности и `reset` `main` может уехать, и выкатится
не то, что доказывали. Поэтому сначала — sha, и дальше весь выкат только
против него.

```bash
ssh doctor 'cd ~/mara-second-brain
  git rev-parse origin/main
  git log --name-only --no-renames --pretty=format: origin/main..HEAD | sort -u | sed "/^$/d"'
```

**Выписать sha в протокол и дальше подставлять его буквально, вместе с
кавычками.** Переменной shell тут не обойтись: каждый шаг — своя сессия `ssh`,
и `sha=` из этой команды в следующей уже не существует.

Кавычки вокруг дырок — не оформление, а единственная защита от испорченной
подстановки. Промахнуться можно **двумя** способами, и они дают разное.

*Исправлено по кругу 5 (issue #94 п. 7).* Прежняя таблица моделировала пустую
переменную shell — то, что абзац выше прямо запрещает: sha подставляется
буквально, переменных здесь нет. Вывод («кавычки нужны») верен, но основание
было не то. Ниже — оба реальных промаха, всё измерено в одноразовом
репозитории:

**Промах А: дырку забыли заполнить,** в команде осталось буквально `<sha>`.

| команда | без кавычек | в кавычках |
|---|---|---|
| `git reset --hard <sha>` | bash `rc=2`: `syntax error near unexpected token` — `<sha` это перенаправление ввода, а `>` в конце строки некуда направить | `fatal: ambiguous argument '<sha>'`, `rc=128` |
| `git diff --quiet <sha> HEAD -- <пути>` | нет файла `sha` → `rc=1`; **есть файл `sha` → `rc=0` и в корне checkout создаётся файл `HEAD`** | `fatal: bad revision`, `rc=128` |

Вторая строка — не курьёз. `<sha>` без кавычек bash читает как «ввод из файла
`sha`, вывод в файл `HEAD`», сама команда становится `git diff --quiet -- <пути>`
на чистом дереве, то есть `rc=0` — «избыточность доказана» из ничего, да ещё и
с мусорным файлом `HEAD` в корне. Измерено: файл появился, `rc=0`.

**Промах Б: дырку стёрли, вставив пустоту** (буфер обмена был пуст).

| команда | без кавычек (аргумент исчез) | в кавычках (пустая строка) |
|---|---|---|
| `git reset --hard` | `rc=0`, сброс на **текущий** HEAD, незакоммиченное затёрто, протокол зелёный | `fatal: ambiguous argument ''`, `rc=128` |
| `git diff --quiet HEAD -- <пути>` | `rc=0` на чистом дереве — снова доказательство из ничего | `fatal: bad revision ''`, `rc=128` |

`rc=128` и `rc=2` этот ранбук трактует верно уже ниже («команда сломалась,
читать текст ошибки»). В кавычках **оба** промаха громкие, без кавычек каждый
имеет свою тихую ветку — и обе дают **зелёный протокол над невыкаченным
деревом**.

**Три исключения, где кавычек мало.** Проверка миграции в конце этого шага
отдаёт `git` в конвейер, и `rc` там принадлежит `grep`, а не `git` — поэтому в
ней стоит отдельный `echo "git rc=$?" >&2`. Шаг 5 достаёт путь из `ExecStart`, и
пустая переменная там не ломает `git -C` вовсе — поэтому там `exit 1`, а не
`echo rc=$?`. Третье — проверка зелёности коммита ниже в этом же шаге: `gh`
пустой аргумент фильтра просто игнорирует, и кавычки там бессильны в принципе.
Все три места отмечены на месте.

Третье исключение стоит разобрать отдельно, потому что оно было найдено уже в
круге 4 — то есть таблица выше два круга считала себя полной и не была. Первая
редакция звала `gh run list --commit "<sha>" --limit 5`, и вот что это даёт:

| подстановка | rc | вывод |
|---|---|---|
| `--commit ""` | **0** | пять строк `completed success` — **чужих** коммитов |
| без `--commit` вовсе | 0 | байт в байт то же |
| короткий sha | 0 | пусто |
| несуществующий sha | 0 | пусто |
| полный sha | 0 | одна зелёная строка |

То есть незаполненная дырка печатала зелень посторонних прогонов, а «зелено»,
«прогонов нет», «sha неверный» и «sha короткий» были неразличимы. Шаг 1 при этом
отдаёт оператору именно короткие sha (`git log --oneline`).

Второй вывод — **список путей, которые трогают локальные коммиты**, полученный
командой, а не набранный руками. Он идёт в протокол: список из головы нельзя
проверить, а опечатку в пути `git diff` не заметит (`git diff --stat A B --
нет/такого/пути` даёт пустой вывод и `rc=0` — то есть «пусто» одинаково
читается и как «совпало», и как «я промахнулся»).

**Сначала — есть ли что доказывать.** Если шаг 1 показал пустой
`git log --oneline origin/main..HEAD` **и** пустой
`git branch -v --no-merged origin/main`, локальных коммитов нет нигде, список
путей пуст, и весь этот блок **пропускается целиком**: идти к проверке зелёного
коммита.

Вторая команда здесь не для симметрии. `origin/main..HEAD` доказывает
избыточность **только для текущей ветки**, а шаг 3 делает `git checkout main` —
то есть после первого же выката по этому ранбуку ветка `deploy/…` со своими
коммитами остаётся жить в стороне, и `origin/main..HEAD` её больше не видит
никогда. Ничего при этом не теряется (`reset --hard` не собирает коммит,
достижимый из ref-а), но формулировка «локальных коммитов нет» стала бы
неправдой при каждом следующем выкате. Непустой вывод `--no-merged` значит:
блок не пропускать, пути брать из этих веток. Нашёл круг 1 ревью PR #98. После первого же выката по этому ранбуку doctor стоит на `main` без
локальных коммитов — то есть пустой список станет нормальным путём, а не
исключением.

Пропуск здесь не послабление, а защита от ложного красного. Дырку
`<пути из предыдущей команды>` нечем заполнить, а заполненная пустотой команда
превращается в сравнение **всего дерева**:

```
git diff --quiet "<sha>" HEAD --   →   rc=1
```

и это `rc=1` не «незалитая работа», а «HEAD ещё не сдвинут на целевой sha» —
то есть ровно то состояние, в котором шаг 2 и обязан находиться. Измерено в
одноразовом репозитории: HEAD на коммит позади sha, путей нет → `rc=1`.
Прежняя редакция велела читать `rc` и на `rc=1` останавливаться, выхода из
останова не давала, и первый же нормальный выкат встал бы на ровном месте
(issue #94 п. 1).

Доказательство избыточности — числом, не пустотой:

```bash
ssh doctor 'cd ~/mara-second-brain
  git diff --quiet "<sha>" HEAD -- <пути из предыдущей команды>; echo rc=$?'
```

`rc=0` — расхождений нет, работа локальных коммитов уже в `main`. `rc=1` —
**остановиться**: это незалитая работа, её оформляют PR-ом, а не затирают.
`rc=128` — команда сломалась, читать текст ошибки.

Проверить, что целевой коммит зелёный (`enforce_admins` включён с 2026-09-11,
но красный коммит мог попасть в `main` и до этого):

```bash
gh api repos/hleserg/mara-second-brain/commits/"<sha>"/check-runs \
  -q '[.check_runs[]|.conclusion]|@csv'
```

Ждём `"success","success"` и `rc=0`. **Меньше двух прогонов — остановиться**:
обязательных проверок в защите ветки ровно две, `python` и `kotlin`
(`gh api repos/hleserg/mara-second-brain/branches/main/protection`), и одна
зелёная означает, что вторая не приходила. Любой `conclusion`, кроме `success`,
— тоже стоп.

Незаполненная дырка здесь падает громко, в отличие от `gh run list`:
`HTTP 422: No commit found for SHA: /check-runs`, **rc=1**. Неверный sha — то же
самое. Короткий sha этот эндпоинт принимает.

**Что несёт диапазон по схеме реестра:**

```bash
ssh doctor 'cd ~/mara-second-brain && git diff "<старый HEAD>" "<sha>" -- scripts/; echo "git rc=$?" >&2' \
  | grep -inE '^[+-].*(def connect|_ужать_ledger|alter table|create table|rename to|drop table|drop column|user_version|ЛЕДЖЕР)'
```

`echo "git rc=$?" >&2` здесь обязателен, и это исключение из таблицы выше.
Конвейер отдаёт код **последней** команды, то есть `grep`, а `grep` без
совпадений даёт `1` — тот же `1`, что и при «диапазон чист». Сломанный `git` от
пустой дырки съедается конвейером целиком: `git diff "" "" -- scripts/ | grep …`
и `git diff HEAD HEAD -- scripts/ | grep …` дают одинаковый пустой stdout и
одинаковый `rc=1`, отличаясь только текстом на stderr. Это **единственная точка
решения Г4 в документе**, и снимать её с пустоты stdout нельзя. Нашёл круг 3.

`grep -inE`, а не `-nE`: расширение шаблона обосновано будущим кодом, а будущий
код может написать `CREATE TABLE` и `PRAGMA user_version` заглавными. Сегодня в
`scripts/*.py` заглавных среди них нет вовсе, так что `-i` не стоит ничего.

Числа совпадений здесь нарочно нет. В прежней редакции стояло «19 совпадений»,
а их было 28 на всех проверенных ревизиях — цифру никто не пересчитывал при
каждом коммите, и она гнила молча (issue #94 пп. 4-5). Утверждение, которое
обязано быть верным всегда, пишется без числа, которое верно только сегодня.

Смотрим весь `scripts/`, а не только `mara_ingest.py`, и шаблон шире имён из
сегодняшнего кода: помощник миграции, дописанный в тело `connect()`, не изменит
строку `def connect` и без `alter table` прошёл бы мимо. На реальном диапазоне
узкая версия срабатывала (13 совпадений на `e55dfc8~1..dca824f`), но
срабатывать она должна не только на уже известной миграции.

Непустой вывод значит, что выкат несёт миграцию реестра, и дальше идти
**только через гейт Г4**: свежая резервная копия с известным путём и sha,
пройденное учение восстановления (Т3б.1), явное разрешение владельца. Не
«вроде там ничего страшного», а три условия.

Прогон 1 (2026-09-11 04:19): пусто (проверено `git diff --stat origin/main HEAD --`
по списку из пяти путей; работа ушла в `main` как PR #83 и #84). **А вот
проверки на миграцию в тот прогон не было, и она бы сработала:** диапазон
нёс `e55dfc8` (PR #79), где `_ужать_ledger()` перестраивает `commitments`,
`conversations` и `projections` целиком (`rename to *_old` → `create table` →
`insert select` → `drop table`), и делает это из `connect()`, то есть при
первом же открытии базы — кроном или рестартом демона. Гейт Г4 был пройден
мимо, не заметив. Постфактум: во всех трёх таблицах **0 строк**
(`select count(*)`), `*_old` не осталось, терять было нечего — но узнал я это
после, а не до. Отсюда и этот шаг.

## 3. Точка возврата и выкат

Тег дешевле сожалений: он держит старый HEAD достижимым после `reset`. Имя с
временем, а не только с датой: повтор в тот же день иначе падает на «tag
already exists» с `rc=128`, и под `&&` **вся цепочка встаёт** — выкат
прерывается на первом же шаге, а оператор читает про тег и ищет беду в
`reset`. Проверено: `git tag <существующий> HEAD && echo …` → `rc=128`, `echo`
не выполняется.

Имя тега печатается в протокол отдельной командой: `git tag` на успехе молчит,
а откатываться потом надо по имени.

Команды сцеплены `&&` нарочно. Без сцепки упавший `git checkout main`
(незакоммиченное перекрыло переключение) не помешает `git reset --hard`
отработать **на ветке выката** и сдвинуть её на `main`.

Демон гасится до сброса и поднимается после шага 4. Иначе между сбросом и
рестартом на одной базе работают два поколения кода: кроновый процесс откроет
базу уже **новым** кодом под ещё **старым** демоном — и миграцию из шага 2
выполнит он.

Кто именно открывает реестр (по `grep -l "mi.connect("` против
`install/mara.cron`, а не по памяти): `contextd_reconcile.py` в :07 каждого
часа и в 8:00, `core-backup.py` в 4:10, `blob_retention.py` в 4:40.
`context_pack.py` импортирует `mara_ingest`, но `connect()` не зовёт;
`codex-usage.py` к базе не ходит вовсе (`grep -c "sqlite\|mara_ingest"` → 0),
хотя первая редакция этого ранбука называла именно его.

Из этого списка важнее всех 4:10: это **бэкап**. Выкат с миграцией, сделанный
в полночь, к утру получит перестройку руками того самого прогона, который Г4
требует как предусловие, — и копию уже после неё.

```bash
ssh doctor 'sudo systemctl stop contextd'
ssh doctor 'cd ~/mara-second-brain
  t=deploy-before-$(date +%Y%m%d-%H%M%S) \
    && git tag "$t" "$(git rev-parse HEAD)" \
    && echo "тег: $t" \
    && git checkout main -q \
    && git reset --hard "<sha>" \
    && git rev-parse HEAD && date -Is'
```

**Напечатанный HEAD обязан совпасть с `<sha>`.** На шаге 5 это проверяет
застава, здесь — пока оператор. Не совпал — стоп, дальше не
идти: это и есть тот случай, когда дырку не заполнили, а `&&`-цепочка всё равно
дошла до конца. Сверять глазами тут дёшево, потому что оба числа в одном
выводе.

Время шага записать в протокол: без него из записи не выводится даже то, что
рестарт был после сброса.

Прогон 1 (2026-09-11 04:19): тег `deploy-before-20260911` на `54f8464`, HEAD стал
`dca824f`. Демон в тот прогон **не гасился**, и окно смешанного кода
восстанавливается числом: `git reflog --date=iso` даёт сброс в
`04:19:15 +0300`, `systemctl show contextd -p ActiveEnterTimestamp --value` —
`Fri 2026-09-11 04:19:26 MSK`. **11 секунд**, не «около минуты». В это окно из
крона не попадал никто (в :19 идёт только `codex-usage.py`, а он к базе не
ходит), поэтому перестройку таблиц выполнил рестарт демона.

Тот же reflog говорит `reset: moving to origin/main`: прогон сбрасывался на
**ветку**, а не на приколоченный sha. Дисциплину из шага 2 сам прогон не
проходил — как и гашение демона.

**Откат** — отдельный шаг, а не абзац: §6а ниже. Здесь важно только то, что
делает возможным его первую команду: тег держит старый HEAD достижимым после
`reset`, и имя тега уже записано в протокол.

Тег и ветка выката живут только на doctor: `git cat-file -t 54f8464` в
репозитории отвечает `fatal: Not a valid object name`. Пропадёт диск —
пропадёт и точка возврата. Пушить тег в публичный репозиторий стоит только
после шага 2: `rc=0` там и означает, что в этих коммитах нет ничего, чего нет
в `main`.

## 4. Крон

`install/mara.cron` — единственный источник правды. Руками `crontab -e` не
править никогда: правка переживёт до первого `--apply` и исчезнет.


## 5. Проверить дерево до подъёма демона

Сломанное дерево лучше обнаружить, пока демон ещё лежит.

```bash
ssh doctor 'cd ~/mara-second-brain
  d=$(systemctl cat contextd | sed -n "s#^ExecStart=[^ ]* \(.*\)/scripts/contextd\.py.*#\1#p")
  [ -n "$d" ] || { echo "путь из ExecStart не извлёкся — СТОП"; exit 1; }
  [ "$(realpath -- "$d")" = "$(realpath -- ~/mara-second-brain)" ] || { echo "юнит смотрит не в этот checkout — СТОП"; exit 1; }
  echo "юнит смотрит в этот checkout"
  git -C "$d" rev-parse HEAD
  [ "$(git -C "$d" rev-parse HEAD)" = "<sha>" ] || { echo "HEAD дерева юнита не совпал с целевым — СТОП"; exit 1; }
  python3 -c "import sys; sys.path.insert(0,\"$d/scripts\")
import contextd, mara_ingest, contextd_reconcile
print(\"импорт ок\", sys.version.split()[0])"'
```

`exit 1` вместо `echo rc=$?` — не стиль, а необходимость. Их здесь три (круг 4
поймал, что прежняя редакция говорила «три», а в блоке стояло два, и третьей
заставой числился собственный ненулевой выход python — не то же самое: он ловит
сломанный импорт, а не расхождение HEAD). `git -C ""
rev-parse HEAD` **не ошибка**: пустой `-C` это no-op, git остаётся в текущем
каталоге и печатает HEAD того дерева, куда сделан `cd`, то есть ровно то число,
которое строка ниже требует сверить с `<sha>`. Проверено: `git -C "" rev-parse
HEAD` → `rc=0` и валидный sha. Единственный вероятный отказ `sed` — пустой
вывод, и он же единственный, которого `git -C` не замечает. Нашёл круг 3 ревью
PR #88: правка круга 2 закрыла «зелёное число над невыкаченным деревом» в
`reset` и завела его же в доказательстве нового кода.

`realpath -- "$d"`, а не `realpath "$d"`. Допишут в юнит флаг интерпретатора
(`-u` — ровно то изменение, которое этот ранбук предсказывает на шаге 6), и `sed`
отдаст `$d` вида `-u /путь`. Без `--` его съедал бы сам `realpath`
(`invalid option -- 'u'`), и шаг останавливался бы с диагнозом про опцию. С `--`
останов тот же, но stderr называет строку целиком, а «юнит смотрит не в этот
checkout» перестаёт быть ложью: извлечённое и правда не checkout. Замерено в
песочнице с подменённым `systemctl`, четыре случая — сходится, чужой sha, пустая
дырка `<sha>`, флаг `-u`; первый `rc=0`, остальные `rc=1`.

`sys.path` тоже берёт `$d`, а не `scripts` от текущего каталога: разойдись
пути — импорт проверял бы не то дерево, чей HEAD только что доказывали.

Первые две строки замыкают связку **числом, а не глазами**: путь берётся из
`ExecStart` самого юнита, сравнивается с checkout, и `git -C` печатает HEAD
именно того дерева, из которого запускается демон. Совпадение с `<sha>` из
шага 3 проверяет **третья застава**, а не оператор: до круга 4 здесь стояло
«этот HEAD обязан совпасть», то есть просьба посмотреть глазами — ровно тот
осмотр, от которого отказывается раздел 0, только на шаг позже. HEAD при этом
печатается по-прежнему: он нужен в протоколе, даже когда застава прошла молча.
Прежняя редакция печатала `ExecStart` и `realpath` рядом и просила увидеть
совпадение уже двух путей.

Путь наружу не печатается нарочно: в `ExecStart` стоит абсолютный путь с
системным именем пользователя doctor, а репозиторий публичный. Сравнение
отдаёт `rc`, не путь.

Импорт трёх модулей — самая дешёвая проверка того, что дерево хотя бы
синтаксически живо на той версии Python, что стоит на doctor (3.12.3). Он идёт
**отдельным** интерпретатором и `connect()` не вызывает, то есть мимо
единственного, что здесь реально может упасть, — перестройки таблиц из шага 2.
Гейт целиком на doctor не гоняем: он идёт в CI и на BetaPi.

Прогон 1 (2026-09-11 04:19): импорт прошёл, но **после** рестарта, а не до; сверки
`ExecStart` с checkout не было. Постфактум она сходится: `rc=0`, HEAD дерева
юнита — `dca824fd2ee806888264cd97bea45f0bbb748816`.

## 6а. Откат

Откат — это тот же выкат, только целевой sha берётся из тега возврата. Значит и
порядок тот же: демон гасится **до** сброса дерева, HEAD проверяется, и шаг 6
проходится целиком. Прежняя редакция описывала откат одним абзацем прозы — без
`ssh`, без гашения демона, без проверки и без ожидаемых значений (issue #94
п. 2). Откат — тот момент, когда руки трясутся сильнее всего, и импровизация в
нём стоит дороже всего.

**Нулевой вопрос: откатывают код или код и базу?** Если шаг 2 показал миграцию
реестра, откат кода в одиночку ничего не чинит и делает хуже: старый код на
ужатых таблицах получит `IntegrityError` там, где раньше писал NULL. Тогда
откат — это код **и** база из той резервной копии, путь и sha которой записаны
до сброса. Нет записанной копии — откатываться нельзя, и это решается до первой
команды.

**1. Погасить демона.**

```bash
ssh doctor 'sudo systemctl stop contextd'
ssh doctor 'systemctl is-active contextd'
```

Ждём `inactive` (у `is-active` при этом `rc=3` — это норма, а не отказ).

**2. Вернуть дерево на тег возврата.**

```bash
ssh doctor 'cd ~/mara-second-brain
  git reset --hard "<тег возврата>" \
    && git rev-parse HEAD && date -Is'
```

Перед сбросом — та же застава, что в шаге 1: `git status --porcelain` должен
быть пуст, кроме заведомо генерируемого. На откате дерево грязное **вероятнее**,
чем на выкате: оператор уже успел поковыряться, пытаясь починить на месте. Тег
держит коммит, а не рабочее дерево, и `reset --hard` затрёт правки без следа.

Имя тега — из протокола шага 3 (`deploy-before-<метка>`), в кавычках и
буквально, по тем же правилам, что и `<sha>` (промах «есть файл `sha`» для тега
невозможен — в дырке `<тег возврата>` пробел, и оба промаха там громкие): промахи из таблицы шага 2 здесь
ровно те же. Напечатанный HEAD обязан совпасть с HEAD **до** выката, который
шаг 1 записал полным, а не коротким. Не совпал — стоп.

**3. База — только если шаг 2 показал миграцию.** И вот здесь ранбук обязан
сказать правду: **`docs/RUNBOOK-restore.md` ещё не написан** (`ls docs/RUNBOOK-*`
— один файл, этот). Его пишет Т3б.1 плана вместе с учением восстановления.
Пока его нет, откат выката с миграцией **не описан ни одной строкой**, то есть
выполнять его придётся импровизацией на трясущихся руках — ровно то, от чего
этот раздел и заводился. Отсюда правило, которое дешевле любого отката: выкат,
несущий миграцию, не начинается, пока Т3б.1 не пройдено. Гейт Г4 требует
учения как предусловия **выката** именно поэтому — к моменту, когда база
понадобилась, тренироваться поздно.

**3а. Пройти шаг 4 — крон.** `install/install-cron.sh --check`, при
расхождении `--apply`. Пропустить его нельзя: если откатываемый выкат менял
`install/mara.cron`, установленный crontab остался от **новой** редакции поверх
**старого** дерева — расписание зовёт скрипты и флаги, которых в коде уже нет.
Обнаружится это ночью, следующим прогоном, а не здесь. Нашёл круг 1 ревью
PR #98: прямой выкат этот шаг делает, а откат его терял.

**4. Поднять демона и пройти шаг 6 целиком** — все проверки, включая путь из
`/proc/<pid>/cmdline`. После отката он обязан читаться как тот же
`~/mara-second-brain/scripts/contextd.py`; HEAD этого дерева теперь старый, и
это единственное отличие от обычного выката.

**5. Записать в протокол,** что откатывались, с какого sha на какой и почему.
Тег и ветка выката не удаляются — см. §7.
