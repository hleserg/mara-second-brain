# Mara Ambient Memory — дизайн ядра

Дата: 2 сентября 2026. Статус: принят владельцем (подход А, декомпозиция на шесть спек).
Источник требований: `docs/TZ-ambient-memory.md` (ТЗ «Mara Ambient Memory»), ссылки вида §7 ведут туда.

Спека покрывает **шаги 1–3 ТЗ §22**: контракт события, сервисную границу `contextd`,
blob store, приём звонка из готовых файлов, ASR, транскрипт, извлечение, карточки в
волте и post-call дайджест. Контекст-брокер, андроид, Telegram, почта, WhatsApp и SMS
живут в отдельных спеках, их границы описаны в §14.

## 0. Что уже есть и на что опираемся

Проверено 2 сентября 2026, не по памяти:

| Факт | Значение |
|---|---|
| doctor | x86 Ubuntu, `sudo` без пароля, свободно 798 ГБ, python 3.12.3, sqlite 3.45.1 |
| ffmpeg на doctor | отсутствует, ставится из apt |
| Свободный порт на doctor | 8788 (8787 занят basic-memory, 8765/8888/8889 докером) |
| doctor → bigpc | напрямую по локалке: ollama `11434` и whisper `8770` отвечают |
| GPU bigpc | занято 10.8 из 16.3 ГиБ, whisper уже в памяти |
| ollama | 0.23.2, `qwen3.5:9b` 6.6 ГБ, structured output по JSON-схеме поддержан |
| whisper на bigpc | `WhisperForConditionalGeneration.generate`, жёсткий потолок 30 с, ответ 413 при превышении |
| мак | `GatewayPorts no`, sudo только с паролем, tailnet-адрес `100.64.0.1` |
| Hermes | плагины умеют `register_tool` и `inject_message`; бот и `TELEGRAM_HOME_CHANNEL` в `~/.hermes/.env` |

Из этого следуют два неочевидных ограничения, которые дальше определяют дизайн:
ASR и извлечение нельзя гонять параллельно (VRAM), а обратный ssh-туннель с doctor не
сможет слушать tailnet-адрес мака.

## 1. Топология и транспорт

```text
телефон ──tailscale──► мак:8788 ──ssh -L──► doctor:127.0.0.1:8788 (contextd)
                                                  │
                                   ┌──────────────┼───────────────┐
                                   ▼              ▼               ▼
                          /srv/mara-blobs   bigpc:8770 ASR   bigpc:11434 извлечение
                                   │
                                   ▼
                             /srv/vault (kb/conversations, kb/commitments)
                                   │
                                   ▼
                        Telegram Bot API ─► дайджест Серёге
```

`contextd` слушает **только loopback** doctor (ТЗ §4: не выставлять наружу). Всё, что к
нему приходит, приходит через ssh-туннель. Наружу в интернет он не смотрит вообще.

**Релей на маке.** launchd-агент `com.mara.relay` держит
`ssh -N -L 100.64.0.1:8788:127.0.0.1:8788 doctor` с `KeepAlive`. Адрес привязки задаёт
клиент, серверный `GatewayPorts` тут ни при чём, поэтому sudo на маке не нужен. Мак
остаётся тупой трубой: ни байта аудио на нём не оседает.

Понадобится ssh-ключ мак → doctor, сейчас есть только обратный. Ключ генерится на маке,
публичная часть кладётся в `authorized_keys` на doctor с ограничением
`restrict,port-forwarding,permitopen="127.0.0.1:8788"`. Этот ключ не даёт ни шелла, ни
доступа к другим портам: если мак угонят, он открывает ровно одну трубу.

Если doctor когда-нибудь заведут в tailnet, релей выкидывается одной строкой: телефон
пойдёт прямо на doctor. Дизайн это переживает без переделки, меняется только базовый URL
в настройках устройства.

**Авторизация устройства.** Заголовок `Authorization: Bearer <token>`. Токен живёт в
таблице `devices` в виде sha256, отзыв это `UPDATE devices SET revoked_at`. Выдаётся
командой `contextd.py --pair <имя>`, которая печатает URL и токен один раз и рисует QR в
терминале. В APK токенов нет (ТЗ §18), устройство получает свой при спаривании.

## 2. Контракт события

Одна форма для всех источников, `mara.event.v1`:

```json
{
  "schema": "mara.event.v1",
  "kind": "call|message|email|notification|correction",
  "source": "phone|telegram|gmail|whatsapp|sms|hermes",
  "source_id": "стабильный id на стороне источника",
  "occurred_at": "2026-09-02T14:05:00+03:00",
  "ended_at": "2026-09-02T14:23:11+03:00",
  "classification": "personal|work-confidential|third-party",
  "dedupe_key": "не принимается: сервер считает сам (см. #26)",
  "payload": { "поля, специфичные для kind" },
  "blob": {"sha256": "...", "bytes": 41234567, "mime": "audio/m4a", "ext": "m4a"}
}
```

**Идемпотентность.** `dedupe_key` считает сервер, присланный клиентом
выбрасывается: `src:` плюс `sha256(source + "\x00" + source_id)`, а для событий
с аудио — `blob:` плюс sha256 самого аудио. Блок `blob` принимается только у
`kind: "call"`, и `sha256` в нём обязан быть 64 шестнадцатеричными знаками.
Колонка `UNIQUE`, повторный POST возвращает
`200 {"duplicate": true, "event_id": ...}` и не создаёт вторую работу. Существование
файла карточки как признак дубля (нынешний приём в репо) для потокового приёма не
годится: имя карточки зависит от контакта, который резолвится позже. Файл
`_system/ingest-state.json` из ТЗ §3 не строим, его никогда не существовало, реестр живёт
в SQLite демона.

**Аудио заливается в два шага.** Сначала событие с хешем и размером; сервер отвечает,
нужен ли ему блоб (`"need_blob": true|false`). Потом `POST /v1/ingest/audio?event=<id>`
сырыми байтами. Сервер считает sha256 полученного и при расхождении отвечает `409` и
удаляет частичный файл. Расхождение хеша успехом не считается (ТЗ §20).

Событие при `409` переводится в `stale` и больше никого не ждёт: телефон на этот код
пересчитывает файл с начала, а дописанный за время чтения файл даёт другой хеш —
другой `source_id`, другой ключ дедупа, новая строка. Долить старую уже некому, и
`stale` нужен ровно чтобы она не поднимала «запись не долита» каждый час до конца
времён. Обратный ход остался: если хеш не изменился (порча в канале при неизменном
файле), телефон попадёт по дедупу в ту же строку и дольёт её — приём блоба принимает
и `new`, и `stale`.

## 3. contextd: процесс и поверхность

Один systemd-юнит `contextd.service` на doctor, `User=sergey`, `Restart=always`. Внутри
`http.server.ThreadingHTTPServer` из стандартной библиотеки и `sqlite3`. Ни одной новой
зависимости: ни fastapi, ни redis, ни postgres (ТЗ §4, §23).

Демон **тонкий**. Он принимает, кладёт в очередь, отдаёт статус и метрики. Тяжёлое
делают те же однофайловые скрипты, что уже живут в `scripts/`, демон запускает их
подпроцессом и читает JSON со stdout. Так пайплайн остаётся отлаживаемым руками:
`python3 scripts/call-asr.py --event <id>` работает и без демона.

```text
POST /v1/ingest/event      → {"event_id","job_id","duplicate","need_blob"}
POST /v1/ingest/audio      → {"event_id","blob_sha256","bytes"}
POST /v1/ingest/message    → тонкая обёртка над event, kind=message
POST /v1/ingest/email      → тонкая обёртка над event, kind=email
GET  /v1/jobs/{id}         → {"state","attempts","next_at","last_error"}
GET  /v1/context/bootstrap → пакет контекста (в этой спеке: now-скелет и последний дайджест)
POST /v1/context/query     → резолв сущностей и релевантные пакеты (спека 2)
GET  /healthz              → {"ok":true,...}
GET  /metrics              → текстовый формат Prometheus, без сервера метрик
```

Схема SQLite (`/srv/mara-blobs/contextd.db`, вне волта и вне git):

```sql
devices  (id, name, token_sha256, created, last_seen, revoked_at)
events   (id, kind, source, source_id, dedupe_key UNIQUE, device_id,
          received, occurred, ended, classification, payload_json,
          blob_sha256, state)
-- events.state: new → stored → transcribed → extracted → projected → done,
-- плюс тупик stale (телефон объявил один хеш, а прислал байты с другим)
jobs     (id, event_id, kind, state, attempts, next_at, last_error,
          created, updated, lease_until)
blobs    (sha256 PRIMARY KEY, path, bytes, mime, created, pin,
          audio_until, purged_at)
digests  (id, event_id, chat_id, text, items_json, sent_at, state)
```

`digests.items_json` нужен для коррекций: когда Серёга отвечает «это тоже задача, срок
пятница», надо знать, о каком пункте последнего дайджеста речь.

Воркер — тред внутри демона, берущий работы по `lease_until` (аренда 10 минут, чтобы
упавший процесс не подвесил работу навсегда). GPU-работы (`asr`, `extract`)
сериализуются одним семафором на единицу: на bigpc свободно меньше шести гигабайт,
параллельный запуск вытеснит whisper и обе работы поедут медленнее, чем одна.

## 4. Blob store, манифест, ретеншен

```text
/srv/mara-blobs/
  calls/2026/09/<sha256>.m4a          # аудио, права 0600, владелец sergey
  manifests/<event_id>.json           # неизменяемый манифест
  transcripts/<event_id>.jsonl        # сегменты со спанами
  contextd.db
```

Каталог создаётся с `chmod 700`, лежит вне волта, вне git и вне фильтров R2 — аудио
физически не может попасть в синк (ТЗ §12, §23). Ключ доверия это content hash плюс id
события, а не имя файла из телефона (ТЗ §7).

Манифест неизменяемый и вложенный, потому что это JSON, а не фронтматтер:

```json
{"id":"call_<uuid>","type":"call","source":"phone","source_id":"...",
 "started_at":"...","ended_at":"...","direction":"incoming|outgoing|unknown",
 "participants":["person:sergey","person:unknown"],
 "classification":"personal","sensitive":true,"cloud_allowed":false,
 "recording":{"producer":"huawei-native|external-recorder|unknown",
              "audio_sha256":"...","blob_ref":"local://calls/2026/09/<sha>.m4a",
              "codec":"aac","channels":1},
 "processing":{"pipeline_version":1},
 "retention":{"audio_until":"2026-12-01","transcript_until":null},
 "purged":null}
```

**Ретеншен.** Аудио 90 дней по умолчанию, транскрипт и выжимка бессрочно и только
локально, `pin: true` отменяет удаление конкретной записи. Уборка идемпотентна: скрипт
`blob-retention.py` удаляет файл, дописывает в манифест `purged: {"at": ..., "reason":
"retention"}` и оставляет сам манифест навсегда. Повторный прогон по уже удалённому
блобу ничего не делает и не считается ошибкой.

Почему вложенность допустима здесь и запрещена в карточке: парсер фронтматтера в репо
(`scripts/vault_common.py` и `frontmatter-migrate.py`) понимает только плоские скаляры и
плоские списки. Вложенная карта в карточке молча распарсится в мусор. Поэтому всё
вложенное живёт в манифесте, а в карточку идут плоские ключи вида
`retention_audio_until`.

## 5. ASR

Работа `asr` делает пять шагов на doctor:

1. `ffprobe` берёт длительность и кодек;
2. `ffmpeg` нормализует в моно 16 кГц WAV;
3. режет на куски по 25 секунд с перекрытием 2 секунды;
4. шлёт каждый кусок в `POST http://<bigpc в локалке>:8770/transcribe` сырым WAV;
5. склеивает в JSONL, где `start_ms/end_ms` это границы куска в исходной записи.

Формат сегмента ровно как в ТЗ §8:

```json
{"segment_id":"s0001","start_ms":0,"end_ms":25000,"speaker":"unknown-A",
 "text":"...","asr_confidence":null,"speaker_confidence":null}
```

Точность спанов на этом шаге — кусок, то есть до 25 секунд. Это честно и достаточно,
чтобы «показать цитату» открыло нужное место записи. Пословные таймстемпы требуют
`return_timestamps=True` в `generate` и правки `/root/tts/server.py`, а этот файл
принадлежит проекту голосовой маски, не этому репо. Правку оформляем отдельным шагом
позже, когда точность станет мешать; в спеке она названа, чтобы не выглядеть сюрпризом.

**Диаризация не блокирует пайплайн** (ТЗ §8). Если раздельных каналов нет и pyannote
недоступен, все сегменты получают `speaker: unknown-A`, транскрипт сохраняется,
извлечение идёт дальше. Работа `diarize` появляется позже и переписывает только поле
`speaker`, не трогая текст и спаны.

**Если bigpc выключен** (а он не круглосуточный), работа не падает, а уходит в ретрай по
расписанию из ТЗ §17. Аудио уже лежит на doctor, терять нечего. Fallback на whisper мака
не делаем: base-модель на восьмигиговом M1 даст качество хуже, чем ожидание, а очередь
ждать умеет.

## 6. Извлечение смысла

Локально, на bigpc, `ollama /api/chat` с моделью `qwen3.5:9b`, `temperature: 0`, `format`
= JSON-схема из ТЗ §9. Ни один байт транскрипта не уходит во внешний API (ТЗ §9, §18).
Промпт живёт в волте, `_system/prompts/call-extract.md`, рядом с существующими
промптами дистиллятора.

Схема даёт `requests`, `commitments`, `decisions`, `constraints`, `open_questions`,
`changed_instructions`, `people_mentioned`, `projects_mentioned`, `followups`. Правила,
которые проверяются тестами:

- явная просьба и предположение — разные вещи, `explicit` не выдумывается;
- дедлайна нет, если его не произнесли: `deadline_explicit: false` и пустой `due_at`;
- «до пятницы» превращается в дату относительно `occurred_at`, но исходная фраза
  сохраняется рядом в `deadline_phrase`;
- «побыстрее» датой не становится;
- у каждого пункта обязателен `evidence` со спанами, пункт без спана выбрасывается;
- новое противоречащее поручение не стирает старое, а создаёт `supersedes` и проставляет
  `valid_until` предыдущему.

Пороги (конфигурируемые, дефолт из ТЗ §9):

| Уверенность | Что происходит |
|---|---|
| ≥ 0.85 | карточка в `kb/commitments/` со статусом `proposed` |
| 0.60–0.85 | строка «Возможно задача» в дайджесте, карточка не создаётся |
| < 0.60 | ничего |

Если модель недоступна, транскрипт остаётся, работа уходит в ретрай, данные не теряются.

## 7. Проекция в волт

Карточка разговора `kb/conversations/2026-09-02-1405-anna.md`:

```yaml
---
title: Звонок с Анной, 2 сентября 14:05
type: conversation
source: phone
source_id: call/<uuid>
created: 2026-09-02T14:31:00+03:00
occurred: 2026-09-02T14:05:00+03:00
sensitive: true
domain: personal
classification: personal
storage_scope: vault-sync
model_scope: local-only
cloud_allowed: false
audience:
  - mara
retention_audio_until: 2026-12-01
content_sha256: <sha256 тела карточки>
source_revision: 1
pipeline_version: 1
valid_from: 2026-09-02T14:23:11+03:00
---
Люди: [[anna]]
Проекты: [[remont]]

## Попросили
- Прислать смету до пятницы · 04:12

## Ты обещал
- Позвонить в понедельник · 11:40

## Решили
- Плитку берём керамогранит · 07:55

## Неясно
- Кто платит за доставку · 09:02
```

Всё плоское. `audience` — список, парсер плоские списки понимает. Тело содержит строки
`Люди:` и `Проекты:` в том виде, который единственный понимает `entity-link.py`.

Карточка обязательства `kb/commitments/2026-09-02-smeta-anne.md` содержит `owner`,
`promised_to`, `due`, `due_explicit`, `status` (`proposed|accepted|done|dropped`),
`origin` со ссылкой на разговор и `supersedes`, если она заменяет предыдущую.

Три правки в существующие скрипты, без них звонки не видны системе:

1. `daily-page.py` сканирует четыре папки `kb/`; добавляем `conversations` и
   `commitments`.
2. `daily-summary.py` выбрасывает заметки без `project:`; для типов `conversation` и
   `commitment` это правило не применяется.
3. `entity-link.py` людей никогда не создаёт сам. Появляется одно исключение: человек
   заводится из разрешённого контакта журнала звонков, где имя даёт адресная книга, а не
   текст. Упоминание в разговоре по-прежнему человека не создаёт.

Записи атомарные (`tmp` плюс `os.replace`) и под общим флоком `vault_common.locked`, как
все остальные писатели волта. Время `occurred` считается по `MARA_TZ_HOURS`, а не по
часам хоста, иначе «вчера» разъедется на три часа.

## 8. Дайджест и коррекции

Текст дайджеста рендерится **без модели**, шаблоном по извлечённому JSON. Формат ТЗ §16:
заголовок со временем и контактом, затем «Попросили», «Ты обещал», «Создано», «Возможно
задача», «Изменилось», «Неясно». Пустые разделы не печатаются.

Отправка: прямой `POST` в Telegram Bot API с doctor, токен и `TELEGRAM_HOME_CHANNEL`
из `/etc/mara/contextd.env`
(права 0600, вне волта и вне git). Через Hermes не идём сознательно: `inject_message`
запускает полноценный ход модели, то есть дайджест стоил бы одного вызова LLM и мог бы
быть переписан ею; к тому же он должен доходить, когда Мара занята или лежит.

Дайджест сохраняется в таблицу `digests` вместе с пунктами. Ответ Серёги обычной фразой
обрабатывает инструмент Мары `mara_correction` (спека 2): он тянет последний дайджест
через `/v1/context/bootstrap`, понимает, к какому пункту относится «это», и шлёт
`kind: correction` обратно в contextd. YAML руками никто не правит (ТЗ §16).

## 9. Очередь, ретраи, DLQ, реконсиляция

Расписание из ТЗ §17: сразу, +1 м, +5 м, +30 м, +2 ч, +12 ч, потом DLQ. Джиттер ±20 %,
чтобы после перезагрузки bigpc все работы не ударили одновременно.

DLQ это `state='dlq'` в той же таблице, отдельной админки нет. Раз в сутки, вместе с
утренней сводкой, Мара сообщает только реальные проблемы: сколько работ застряло и по
какой причине. Одна строка, а не дамп.

Реконсиляция (`contextd-reconcile.py`, крон раз в час) проверяет пять инвариантов из
ТЗ §17, которые применимы к этой спеке:

- манифест есть, блоба нет и он не помечен `purged` — событие в DLQ с понятной причиной;
- блоб есть, манифеста нет — осиротевший файл в отчёт, не удалять молча;
- транскрипт есть, работы `extract` нет — поставить;
- карточка есть, Basic Memory её не проиндексировал — посчитать лаг;
- ретеншен просрочен — поставить работу уборки.

## 10. Безопасность и граница облака

`sensitive: true` сегодня единственный флаг, который **реально** что-то запрещает:
`queue-worker.py` держит такие карточки вечно и не шлёт в OpenRouter, `daily-summary.py`
их пропускает. Поля `cloud_allowed` и `model_scope` из ТЗ §10 — декларация без
исполнения. Поэтому:

1. карточки разговоров и обязательств получают и `sensitive: true`, и новые поля;
2. в `queue-worker.py` добавляется одна проверка: `cloud_allowed: false` держит карточку
   так же, как `sensitive: true`;
3. фикстура `tests/fixtures/private-call.md` с `cloud_allowed: false` и тест, который
   падает, если облачный адаптер её увидел. Это и есть требуемый ТЗ §18 тест, ломающий
   сборку.

Остальное по §18: секретов в волте нет и не появляется, `scrub()` из `vault_common`
применяется к каждому тексту перед записью; логи демона не содержат тел сообщений и
транскриптов, только идентификаторы, размеры и состояния; `contextd.db`, токены и
`/etc/mara/contextd.env` в `.gitignore` и вне волта; отзыв устройства одной командой.

**Граница синка.** Решение владельца «синкать всё» относится к карточкам: в R2 и на
устройства едут только дистиллированные карточки разговоров и обязательств. Аудио,
JSONL-транскрипты и сырые уведомления остаются в `/srv/mara-blobs`, который в синк не
входит вовсе. Это примиряет решение с запретом ТЗ §18 на сырые тела в R2. В инструкцию
владельца добавляется пункт: исключить `kb/conversations` из индекса Copilot на всех
устройствах, иначе индекс уедет в облако вместе с личным.

## 11. Наблюдаемость

`GET /metrics` отдаёт текст в формате Prometheus, считая всё на лету запросами к SQLite.
Никакого сервера метрик, Grafana не заводим (ТЗ §19). Из списка ТЗ в этой спеке живут:
`mara_ingest_queue_depth`, `mara_ingest_lag_seconds`, `mara_dlq_count`,
`mara_transcription_queue_depth`, `mara_transcription_realtime_factor`,
`mara_task_extraction_failures_total`, `mara_mobile_last_seen_seconds`,
`mara_mobile_pending_uploads`. Сверх списка ТЗ заведён `mara_ingest_stale_events`:
он считает брошенные события, и его рост при каждом звонке означает, что диктофон
дописывает файл после того, как телефон его посчитал. Остальные появятся вместе со
своими источниками.

`GET /healthz` и `contextd.py --self-check` дают человекочитаемый отчёт: доступность
bigpc, глубина очереди, возраст последнего события, свободное место под блобы.
`--self-check` есть у каждого нового скрипта, как у остальных тринадцати в репо.

## 12. Тесты

В репозитории нет ни `tests/`, ни CI. Заводим `tests/` с прогоном через `unittest` из
стандартной библиотеки и один скрипт `scripts/run-tests.sh`, который гоняет и их, и все
`--self-check`. Без pytest и без фреймворков.

Из ТЗ §20 в этой спеке проверяются:

- повторная заливка того же аудио не создаёт второй звонок;
- частичный файл не принимается (расхождение sha256 → 409);
- расхождение хеша не считается успехом;
- цепочка манифест → ASR → транскрипт → извлечение → карточка на фикстуре;
- аудио не попадает ни в git, ни под фильтры R2;
- облачный адаптер не вызывается при `cloud_allowed: false`;
- явная просьба даёт задачу, предположение не даёт;
- явный дедлайн парсится, размытый не выдумывается;
- у каждого пункта есть спан;
- новое поручение вытесняет старое через `supersedes`, история остаётся.

Тесты извлечения гоняются на фиксированных JSON-ответах модели, а не на живой ollama:
модель недетерминирована, а проверяем мы правила, а не её настроение. Отдельный
медленный тест с живой моделью помечается и в обычный прогон не входит.

## 13. Чего в этой спеке нет

Сознательно не делаем: диаризацию (позже, отдельной работой), пословные таймстемпы
(правка чужого файла, когда понадобится), fallback ASR на маке (очередь ждёт дешевле),
зеркало обязательств в SQLite (полсотни карточек сканируются за миллисекунды), веб-интерфейс
(ТЗ §23), векторную базу (ТЗ §23), Redis и Postgres (ТЗ §4).
