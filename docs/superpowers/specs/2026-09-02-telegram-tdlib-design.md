# Telegram через TDLib — личный поток в память

Спека 4 по ТЗ «Mara Ambient Memory» (§11, порядок §22 пункт 6).
Предыдущие: [ядро приёма](2026-09-02-ambient-memory-design.md),
[контекст-брокер](2026-09-02-context-broker-design.md),
[Mara Capture](2026-09-02-mara-capture-design.md).

## Зачем

Обязательства рождаются не только в звонках. Половина «я тебе пришлю» и
«давай в пятницу» живёт в личном телеграме, и пока туда никто не смотрит,
карточка обязательства появляется только если Серёга сам сказал об этом Маре.
ТЗ §11 требует полный личный поток через TDLib как пользователя — не Bot API,
потому что бот видит только то, что ему написали.

## Что это НЕ делает

Не извлекает обязательства из сообщений. Здесь только приём: сообщение
попало в базу приёма тем же контрактом, что и звонок. Извлечение
(`call_extract` поверх переписки, а не транскрипта) — следующая нарезка,
когда будет видно, как выглядит реальный поток.

Не качает вложения. Метаданные (тип, mime, размер, имя) — да, тело — нет.
ТЗ §11: «скачивание по policy, не бездумно всего подряд». Политики нет, значит
нет и скачивания.

Не читает чаты с ботами и каналы. Чат с самой Марой уже целиком ложится в
память через `hermes-ingest.py`, второй раз он не нужен. Каналы — новости, а
не переписка; обязательств в них нет по определению. Оба исключения — одна
константа `ПРОПУСКАЕМ`, не настройка.

Не отправляет ничего в Telegram. Демон только читает.

## Где что лежит

`doctor` — trusted host по ТЗ §11. TDLib берётся готовым: колесо
`python-telegram 2.0.0` несёт `libtdjson.so` (TDLib 1.8.66), и оно грузится
на Ubuntu 24.04 без сборки. Отдельный venv `~/.local/share/mara/venv-tdlib`,
потому что в рабочем venv уже стоит `python-telegram-bot` с тем же именем
пакета `telegram` — они не уживаются в одном дереве.

Состояние демона — в `/srv/mara-blobs/tdlib/`, рядом с записями звонков и
по тем же причинам: вне волта, вне git, вне R2, каталог `700`:

| Путь | Что |
|---|---|
| `db/` | база TDLib: сессия, кэш чатов, ключи — это и есть авторизация |
| `key` | ключ шифрования базы TDLib, генерится при первом входе, `600` |
| `raw/YYYY-MM-DD.jsonl` | сырой поток апдейтов как есть, append-only (ТЗ §11 разрешает) |
| `cursor.json` | последний принятый `message_id` по каждому чату |
| `heartbeat` | пустой файл, mtime — «демон жив и в связи» |
| `phone` | номер, под которым вошли: `python-telegram` требует его при каждом старте |

Секреты владельца — `api_id` и `api_hash` с my.telegram.org, токен
устройства `tdlib` для contextd — в `/etc/mara/tdlib.env` (`600`, unit
читает его через `EnvironmentFile`). В репозитории лежит только
`install/tdlib.env.example` с пустыми значениями.

Проверяется тестом: каталог состояния не внутри волта и не внутри репо.

## Транспорт: тот же contextd

Демон не пишет в базу приёма напрямую, хотя мог бы — это тот же хост и тот же
пользователь. Он ходит в `POST /v1/ingest/message` на `127.0.0.1:8788` с
токеном устройства `tdlib`. Причина одна: вход в память один, и он покрыт
тестами. Второй писатель в `contextd.db` — это вторая копия правил дедупа,
классификации и логов, которая разъедется с первой через месяц.

Цена — contextd может быть в перезапуске. Поэтому POST не сдаётся: повтор с
паузой до минуты, бесконечно, обработчик апдейтов при этом стоит. Демон
упал, пока стоял, — сообщение лежит в базе TDLib и в `raw/`, и его подберёт
догон по истории (ниже).

## Контракт события

Источник `telegram`, путь `/v1/ingest/message`, `classification: personal`
всегда — ТЗ §11: «private chats/group messages классифицировать local-only
по умолчанию». Групп это касается так же, как личных.

Новое сообщение:

```
source_id: "<chat_id>/<message_id>"
occurred_at: дата сообщения
payload: {
  chat_id, chat_type: private|group|secret, chat_title,
  message_id, sender_id, sender_name, outgoing: bool,
  text, reply_to: message_id|null, thread_id: int|null,
  media: [{type: photo|document|voice_note|video|audio|sticker|…, mime, size, name, duration}]
}
```

**Правки и удаления — отдельные события, а не перезапись.** `put_event`
дедупит по `(source, source_id)`: если бы правка шла с тем же `source_id`,
сервер честно ответил бы `duplicate: true` и выбросил её. Это ровно то, чего
ТЗ §11 запрещает — терять ревизии. Поэтому:

```
правка:    source_id "<chat_id>/<message_id>/edit/<edit_date>"
           payload как у нового + revision_of: "<chat_id>/<message_id>", edit_date
удаление:  source_id "<chat_id>/<message_id>/deleted"
           payload {chat_id, message_id, tombstone_of: "<chat_id>/<message_id>"}
```

Три события в базе, одно состояние наружу: `mara_ingest.message_state(con,
source, key)` сворачивает их — последняя ревизия побеждает, надгробие
возвращает `None`. Это единственная функция, через которую следующая нарезка
(извлечение) будет читать переписку; сырые строки таблицы `events` для неё
не интерфейс. Тест в `test_contextd.py`: новое → правка → удаление = три
события, `message_state` даёт `None`; без удаления — текст правки.

Идемпотентность по `(chat_id, message_id)` из ТЗ §11 — это и есть `source_id`
нового сообщения; повторная доставка того же апдейта (догон по истории после
перезапуска) — `duplicate: true`, ничего не создаётся.

Удаление принимается только `is_permanent && !from_cache`: TDLib шлёт
`updateDeleteMessages` и при чистке своего кэша, это не удаление у человека.

## Догон по истории (ТЗ §17: «Telegram TDLib cursor/history»)

TDLib отдаёт апдейты один раз. Демон, упавший между апдейтом и POST, это
сообщение из апдейтов больше не увидит. Поэтому `cursor.json` и догон:

- при старте и раз в час: `getChats` (основной список, до 200), для каждого
  чата, где `last_message.id` больше курсора, — `getChatHistory` назад, пока
  не дойдём до курсора; каждое сообщение — обычный POST, дедуп отсеет уже
  принятое;
- чат, которого в курсоре нет, — берём последние 100 сообщений, не глубже:
  прошлое до подключения демона не память, а архив;
- курсор двигается только после `200` от contextd.

Правки и удаления, случившиеся пока демон лежал, догон не видит — у истории
нет «что изменилось с тех пор». Это известная дыра, закрывать её опросом всех
старых сообщений дороже, чем она стоит.

## Одноразовый вход

`tdlib_ingest.py --login` в терминале на doctor: телефон, код из Telegram,
пароль двухфакторки если есть (через `getpass`, не эхо). Состояние
авторизации остаётся в `db/`, дальше демон входит сам после любого
перезапуска — «one-time interactive auth, затем daemon» из §11.

`--serve` без авторизации не крутится в цикле: пишет «нет входа, запусти
--login» и выходит с ошибкой. Юнит с `RestartSec=60`, чтобы это не
превращалось в шторм; включать юнит имеет смысл только после входа, так и
написано в шагах владельца.

## Наблюдаемость

`heartbeat` трогается после каждого обработанного апдейта и раз в минуту,
пока TDLib в состоянии `connectionStateReady`. Связи нет — файл стареет.
contextd отдаёт его возраст как `mara_tdlib_lag_seconds` (−1, если демона ещё
не запускали); сверка раз в час поднимает `warn` при возрасте больше часа.

Логи демона: `chat_id`, `message_id`, вид события, код ответа. Текста
сообщений в журнале нет (ТЗ §18). Текст есть в `raw/` — это локальный файл
под `700`, не лог.

## Как это тестируется без Telegram

Разбор апдейта в событие — чистые функции от словарей TDLib, тесты на них
не требуют библиотеки: новое сообщение с текстом и с фото, правка, удаление
из кэша (пропуск) и настоящее, чат с ботом и канал (пропуск), ответ и тред.

Демон — класс с подставляемым клиентом. `--self-check` гоняет его на
фальшивом клиенте: POST ушёл с нужным телом, первая неудача сети не
роняет и не теряет, курсор сдвинулся только после успеха, догон дотянул
сообщение, которого не было в апдейтах. Ни `telegram`, ни `libtdjson` при
этом не импортируются — гейт зелёный и на BetaPi.

## Порядок нарезки

1. `message_state` в `mara_ingest` + тест контракта правок в `test_contextd`.
2. `tdlib_ingest.py`: разбор, демон, догон, `--login`, `--serve`, `--self-check`.
3. `mara_tdlib_lag_seconds` в contextd, проверка в `contextd_reconcile`.
4. Юнит, `tdlib.env.example`, шаги владельца, venv на doctor, устройство `tdlib`.
5. Извлечение обязательств из переписки — отдельная спека, после первых дней потока.

## Вопросы к утру

1. `api_id` и `api_hash`: https://my.telegram.org → API development tools →
   создать приложение, вписать в `/etc/mara/tdlib.env`.
2. Вход: `tdlib_ingest.py --login` на doctor в терминале — телефон, код,
   пароль двухфакторки. Один раз.
3. Включить юнит: `sudo systemctl enable --now tdlib-ingest`.
4. Решить, нужны ли каналы и чаты с ботами когда-нибудь. Сейчас — нет.
5. Ретеншен `raw/` — не задан. Файлы растут; спека 10.
