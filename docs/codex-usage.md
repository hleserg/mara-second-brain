# Codex: квоты и статистика

Локальный JSON для statusline, без записи в волт и без запросов к модели/API:

```bash
python3 scripts/codex-usage.py --status
```

`quotas[]` содержит `window_minutes`, `used_percent`, `remaining_percent`,
`resets_at` (Unix UTC), возраст наблюдения и `stale`. Недельное окно — **10080
минут**, пятичасовое — 300; weekly может находиться в `primary`. Позиция окна
не определяет его длительность. Источник — сохранённые `token_count.rate_limits`,
а не новый запрос баланса: во время простоя свежих показаний нет.
После известного сброса остаток неизвестен (`null`) до следующего показания.

Квота общая для одного аккаунта: зеркала и параллельные сессии не суммируются.
Внутри `(limit_id, window_minutes, resets_at)` берётся максимум использованного
процента. Расхождение reset до 60 секунд считается джиттером одного окна. Старое окно не перезаписывает новое. Расчёт прироста переиспользует
`steps()` Claude: первое показание — baseline, не измеренный расход за период.
В `--status` прогноз использует наблюдавшийся рост за последние 60 минут
(нужно минимум 5 минут), отсутствует при данных старше 10 минут, нулевой скорости
или если сброс наступит раньше исчерпания. Это условная оценка при прежнем темпе,
не прогноз доли выполненной задачи. Разные аккаунты нужно сканировать отдельно
через `--roots`: формат не даёт надёжного идентификатора аккаунта.

## Доставка и отчёты

Существующий `codex-mirror.sh` доставляет JSONL с Linux/WSL/Windows в
`raw/codex/<host>/`. Новый сборщик использует этот же источник:

```bash
python3 scripts/codex-usage.py --vault /path/to/test-vault --dry-run
python3 scripts/codex-usage.py --vault /path/to/test-vault
```

В `Codex Usage/` появляются Dashboard, Daily, Weekly, Models, Projects,
Tools & MCP; в `_data/derived/` — JSONL наблюдений и ответов, summary JSON,
CSV по дням, ISO-неделям, моделям, проектам и сессиям. Все календарные периоды UTC.
Проекты берутся из cwd и приводятся к существующему entity-index.
Расписание `install/mara.cron` пересобирает отчёты каждые 5 минут после его
обычной установки. Клиентская доставка остаётся ежечасной: удалённые отчёты
могут отставать примерно на 65 минут; локальный `--status` видит локальные файлы.
В Markdown записана дата данных, не постоянно устаревающий ETA.

## Правила учёта

- Современные `token_usage_record` учитываются один раз по `response_id`,
  включая копии зеркал и унаследованные записи форков. Для старых CLI используются
  положительные изменения `total_token_usage`, повторные снимки пропускаются.
  Совпадающие thread/cumulative snapshots исключают второй учёт modern/legacy.
  Падение счётчика устанавливает новую базу без выдуманного расхода. Legacy не
  гарантирует точность при обрезанной истории/форках без исходных идентификаторов;
  `legacy_responses` показывает число таких восстановленных ответов.
- Вход включает кэш, выход включает reasoning. Всего = вход + выход; подмножества
  повторно не прибавляются. Цены и списания отсутствуют в источнике:
  `api_usd_equiv` и `actual_spend_usd` равны `null`. Проценты квоты по проектам
  или моделям не выводятся из токенов; коэффициенты Claude здесь неприменимы.
- Инструменты считаются по явным `call_id`; внутренности `functions.exec`, MCP
  и применение skills не угадываются по тексту. В статистике видны имена реально
  записанных вызовов, включая MCP, когда CLI сохраняет их отдельным событием.
- Тексты диалога, reasoning, аргументы и ответы инструментов не экспортируются.
  Только метаданные и счётчики. Markdown проходит существующий scrub; `raw/**`
  и `Codex Usage/_data/**` исключены из R2, отчёты синкаются как обычные заметки.
- Повторный прогон идемпотентен, запись атомарна и защищена общим vault-git lock.
  Неполная последняя JSONL-строка пропускается до следующего прохода. При пустых
  источниках отчёты не перезаписываются. Новых зависимостей и LLM-вызовов нет.

Проверка: `python3 -m unittest tests.test_codex_usage -v`.
Откат: убрать новый cron-job и вернуть предыдущую ревизию; исходные rollout-файлы
не меняются, созданные заметки можно оставить. Живое расписание этот PR не меняет.
