## 1a. Главный вывод относительно §4.1 мастер-ТЗ

Мастер-ТЗ требует: SQLite — единственный authority, Markdown —
перестраиваемая проекция. **Сегодня всё ровно наоборот, и это записано в
самом коде:** `scripts/call_project.py:6-7` — «Волт остаётся источником
правды, SQLite только очередь».

Проверяемые следствия:

- В схеме SQLite (`scripts/mara_ingest.py:28-49`) пять таблиц: `devices`,
  `events`, `jobs`, `blobs`, `digests`. Таблиц обязательств, разговоров,
  сущностей, ревизий, evidence — нет ни одной.
- Статус обязательства живёт только во frontmatter карточки. Его читают
  `context_pack.собрать` (`scripts/context_pack.py:100-107`) и
  `call_project._карточки` (`:306-313`).
- Правка владельца («сделано», «отмени», «срок пятница») меняет строки
  frontmatter на месте (`scripts/call_project.py:345-359`) и дописывает
  журнал правок в тело карточки (`:382`). В SQLite попадает только сам
  факт события-правки (`scripts/contextd.py:259`), но не новый статус.

Отсюда прямое противоречие с §4.8: «пустой волт полностью
восстанавливается из backup ledger + blobs». Сегодня полная пересборка
проекций из базы физически сотрёт все правки владельца, потому что в базе
их нет. Это не недоделка проектора, а перевёрнутая модель authority.
Поэтому Phase 1 мастер-ТЗ нельзя свести к «добавить id в frontmatter»:
переносить придётся сами сущности и историю правок.

Практическое следствие того же корня: ручной ремонт, документированный в
`scripts/contextd.py:6` («чинится руками: `call_project.py --event <id>`»),
перегенерирует карточки из файла извлечения и вернёт `status: done`
обратно в `proposed`. Автоматически это сегодня не происходит:
переигровку проекции ставит только человек, а реконсилятор
(`scripts/contextd_reconcile.py:117-137`) чинит лишь события, у которых
извлечения нет вовсе. То есть риск реальный, но пока ручной.
## 2. Четыре утверждения §2.2, перепроверенные построчно

Эти четыре читались вручную, а не со слов агентов: на них опираются P0-риски.

### §2.2 п. 8 — сервер читает тело загрузки целиком в память

`confirmed`, ровно как записано в ТЗ.

`scripts/contextd.py:197-201` — единственный путь чтения тела:

```python
def body(self):
    n = int(self.headers.get("Content-Length") or 0)
    if n > MAX_BODY:
        raise ValueError("тело больше %d МиБ" % (MAX_BODY >> 20))
    return self.rfile.read(n) if n else b""
```

`MAX_BODY = 512 << 20` объявлен на `scripts/contextd.py:30`. Дальше
`ingest_audio` (`scripts/contextd.py:285-315`) получает готовый `raw`,
считает `hashlib.sha256(raw)` и пишет файл одним `fh.write(raw)`.
Потокового чтения, инкрементального хеша и staging-файла с TTL нет:
`.part` создаётся, но уже из полного буфера в памяти. Пиковая память
процесса — размер загрузки, до полугигабайта на один запрос, плюс копия
байтов внутри `sha256`. Doctor — Raspberry Pi класса ядра, это реальный
риск OOM, а не теоретический.

Хорошая часть: хеш проверяется до `os.replace`, несовпадение даёт `409` и
удаляет `.part`, повтор того же блоба возвращает `duplicate: true`. То
есть идемпотентность и проверка содержимого есть, потоковости нет.

### §2.2 п. 7 — WhatsApp dedupe схлопывает два настоящих сообщения

`confirmed`.

`scripts/whatsapp_import.py:49`: идентификатор сообщения — sha256 от
кортежа «пакет, чат, отправитель, нормализованный текст, минута»:

```python
pkg, chat, sender, normalize(text), at_ms // 60000
```

Два одинаковых «ок» от одного человека в одну минуту дают один и тот же
`source_id`, второе наблюдение отбрасывается сервером как дубль. Это
прямо противоречит §4.4 мастер-ТЗ: «нельзя дедуплицировать два
WhatsApp-сообщения только потому, что совпали sender, text и минута».
Собственный self-check файла (`scripts/whatsapp_import.py:180`) эту
формулу закрепляет как ожидаемое поведение, то есть тест защищает
неверный инвариант и его придётся менять вместе с кодом.

### §2.2 п. 1 и 2 — коллизии имён карточек и идентичность в имени файла

`confirmed`.

- Разговор: `scripts/call_project.py:106` — путь
  `kb/conversations/<день>-<ЧЧММ>-<slug контакта>.md`. Два звонка одному
  контакту в одну минуту дают один путь.
- Обязательство: `scripts/call_project.py:159` — путь
  `<день>-<slug действия, первые 40 символов>.md`, без счётчика. Два
  разных обязательства одного дня, у которых первые 40 символов slug
  совпали, пишутся в один файл, второе затирает первое.
- Для сравнения, ручная задача умеет иначе:
  `scripts/call_project.py:391-395` крутит суффикс `-2`, `-3` до
  свободного имени. То есть механизм в проекте есть, но на карточки из
  звонка он не распространён.

Частичная хорошая новость по идентичности: во frontmatter обязательства
уже есть `source_id` вида `commitment/<event_id>/<секция>/<номер>`
(`scripts/call_project.py:176`), а также `pipeline_version`,
`confidence`, `status`, `origin`, `valid_from`. Это не immutable stable
ID по §4.3 — номер зависит от порядка элементов в выдаче модели, и при
переизвлечении он поедет, — но точка привязки к событию уже есть.

старый список открытых дел, и **ничто его не опровергает**. Модель видит
только устаревшее. Единственное, что спасает, — ответ инструмента правки
в той же истории.

**Пункт 6 хуже, чем записано.** Модель видит в расшифровке метки вида
`[s0001 00:00–00:25]`, а отдавать обязана миллисекунды. Она их
пересчитывает, а не копирует, и проверить пересчёт нечем: функция
нормализации не получает список сегментов вообще. Придуманная метка
доезжает до карточки и дайджеста как правдоподобное `мм:сс`.

## 6. Найдено сверх §2.2

Это не было в списке ТЗ; порядок — по тяжести последствий.

### N1. Тихая потеря аудио при повторе события — P0

`scripts/contextd.py:260`:

```python
need = bool((data.get("blob") or {}).get("sha256")) and not dup
```

`need_blob` считается по признаку «событие новое», а не по признаку
«блоб уже лежит». Телефон трактует ответ буквально
(`Core.kt:137-139`): `200` без запроса блоба переводит работу в `DONE`.

Сценарий отказа целиком: телефон отправляет событие звонка, сервер его
заводит, ответ теряется по дороге (сеть отвалилась, процесс убит).
Работа остаётся в состоянии `HASHED` и повторяется. Сервер отвечает
`duplicate: true, need_blob: false`. Телефон закрывает работу как
успешную и **сам её никогда не повторит**: очередь на телефоне пуста,
событие на сервере навсегда остаётся в состоянии `new` без блоба.

Насколько это молча — точнее, чем звучит. Сервер как раз видит такую
пару: метрика `mara_mobile_pending_uploads` (`contextd.py:189-190`)
считает именно `state='new' and blob_sha256 is not null`, то есть покажет
единицу, а `запись_не_долита` (`contextd_reconcile.py:234-246`) через
сутки поднимет предупреждение «звонков без записи дольше суток». Файл
на телефоне тоже цел: удаления записи после загрузки в коде нет нигде.
Потери байтов, таким образом, нет — есть автоматически невосстановимый
разрыв: догрузить придётся руками, и до этого звонок не пройдёт ни ASR,
ни извлечение. Для §16.2 P02/P03 это всё равно отказ, но отказ
наблюдаемый, а не немой.

Чинится дёшево: считать `need` по факту наличия блоба, а не по
`dup`. Регрессионный тест — повторная отправка события без блоба.

### N2. Полная пересборка проекций сегодня стирает правки владельца — P0

Следствие перевёрнутой authority из раздела 1a. Пока статусы живут
только в Markdown, любая пересборка, которую требует §4.8, — это потеря
данных. Порядок работ в Phase 1 должен это учитывать: сначала перенос
сущностей и истории правок в базу, потом проектор.

### N3. У базы и блобов нет резервной копии вообще — P0

`scripts/vault-backup.sh` кладёт в бэкап только бандл `vault.git`,
шифрует GPG-AES256 и раскладывает по двум локальным носителям, храня
восемь поколений. Поиск по всем скриптам и конфигам не находит ни одного
упоминания `contextd.db` или `mara-blobs` в путях бэкапа.

Без копии остаются: сама база (события, работы, блоб-метаданные,
дайджесты), каталог `calls/` с аудио, `manifests/`, `transcripts/`,
`extractions/`, состояние TDLib и токен Gmail. Волт при этом защищён
трижды: git, бэкап и синк в R2. То есть защищена проекция и не защищён
оригинал. По §5.3 это блокер: пока этого нет, заявлять backup readiness
нельзя.

### N4. Автоматизация Мары живёт только в кроне doctor — P0 по воспроизводимости

См. раздел 3. Двенадцать строк крона заведены руками, установщик пишет
четыре. Восстановление по §5.3 вернёт волт, но не расписание.

### N5. Повторная загрузка в другом месяце создаёт второй файл и вторую работу ASR

`ingest_audio` проверяет существование блоба по пути, который считается
от **сегодняшней** даты (`mara_ingest.blob_path`, `when=None`). Блоб,
принятый в августе, лежит в `calls/2026/08/`, а проверка в сентябре
смотрит в `calls/2026/09/`, не находит и принимает файл заново. Строка в
`blobs` перезаписывается новым путём, старый файл остаётся сиротой, и в
очередь встаёт вторая работа ASR на то же событие.

### N6. Ответы 401 и 413 не вычитывают тело запроса при живом keep-alive

`protocol_version = "HTTP/1.1"`, ответ отдаётся с `Content-Length` и без
`Connection: close`. На отказе авторизации (`authed` возвращает `False`
до чтения тела) и на превышении размера непрочитанные байты остаются в
сокете и разбираются как следующий запрос. Для загрузки звонка это сотни
мегабайт мусора в разборе. Кандидат в причины странных ответов в поле, а
не доказанная причина.

### N7. Гонка в `put_event`

`select ... where dedupe_key=?` и затем `insert` двумя отдельными
операциями в режиме autocommit (`scripts/mara_ingest.py:79-97`). Два
одновременных одинаковых запроса дают `IntegrityError`, который никто не
ловит, то есть 500 вместо честного `duplicate: true`.

### N8. Ни версии схемы, ни внешних ключей

`pragma user_version` равен нулю, `foreign_keys` выключен, миграций нет:
схема накатывается как `create table if not exists` на каждом
соединении. Добавление колонки существующей базе — ручная операция.
Для сравнения, на Android версионирование есть:
`SQLiteOpenHelper(..., "queue.db", null, 3)` с `onUpgrade`.

### N9. Аренда работы короче её тайм-аута

`LEASE_SEC = 600`, а шаг конвейера запускается с `timeout=3600`. Часовой
ASR идёт с просроченной арендой. Сейчас безопасно только потому, что
воркер один и GPU-семафор равен единице; комментарий в коде предлагает
поднять семафор до двух — это сразу даст двойной захват.

### N10. У очереди волта нет DLQ

`scripts/queue-worker.py` — вторая, отдельная очередь (файлы в
`_system/queue/`), не та, что в SQLite. После трёх попыток работа
удерживается навсегда, DLQ нет, счётчик `held` виден только в выводе.
Тестов в `tests/` у файла нет, есть `self_check`, который в unittest не
попадает; то же у плагина Мары.

### N11. Недоставленный дайджест считается успехом

`deliver` вернул `no-transport` — событие всё равно переходит в `done`
(`scripts/call_digest.py:139`). Молчаливая недоставка неотличима от
доставки.

### N12. Временный файл блоба один на хеш

Имя `path + ".part"` фиксировано. Две одновременные загрузки одного и
того же хеша пишут в один и тот же временный файл.

### N13. Запрос без `Content-Length` даёт событие-пустышку

`body()` возвращает `b""`, JSON-маршрут разбирает это как `{}`, и
получается событие с `source=None, source_id=None`. Все такие запросы
схлопываются в один и тот же ключ дедупликации.

## 9. Предлагаемая последовательность PR (§22.5)

Мелкими шагами, каждый сам по себе осмысленный и проверяемый. Первые три
не трогают схему и не требуют миграции.

1. **Этот PR — аудит.** Мастер-ТЗ в репозитории, правила PR-only,
   guardrails агентов, этот документ. Кода не меняет.
2. **Потеря аудио и соседние отказы приёма.** `need_blob` по факту
   наличия блоба (P0-1), путь блоба с датой события вместо сегодняшней
   (N5), вычитывание тела на 401 и 413 (N6), `insert or ignore` вместо
   гонки (N7), недоставленный дайджест не считается успехом (N11).
   Регрессионные тесты на каждый пункт. Ветка `phase0/ingest-losses`.
3. **Бэкап ядра.** База через SQLite backup API, каталог блобов, манифест
   с хешами, проверка восстановления в изолированный каталог, отчёт
   RPO/RTO (P0-2). Ветка `phase2/backup-core`. Состояние TDLib и Gmail в
   бэкап **не** идёт: ТЗ §11 denylist'ит credentials и session-файлы из
   Git, R2 и бэкапов, цена — повторный вход в Telegram и OAuth Gmail
   после восстановления (первая редакция этого пункта требовала обратного,
   это была ошибка).
4. **Воспроизводимая автоматизация.** Крон и таймеры из репозитория,
   `--self-check` на установщик (P0-5). Ветка `phase0/scheduling`.
5. **CI.** GitHub Actions с `run-tests.sh` на каждый push и PR, без
   android-шага. Шаблон PR и CODEOWNERS (P0-10). Ветка `phase0/ci`.
6. **ADR по authority и ID.** Первые два ADR из §21: SQLite как
   authority, формат stable ID. Только документы, без кода, чтобы
   зафиксировать решение до миграции.
7. **Phase 1.** Дальше по §18: схема ledger, ревизии, `expected_version`,
   evidence, проектор. Разбивается на отдельные PR после ADR.

Пункты 2 и 3 стоят раньше всего остального сознательно, но по разным
причинам. Пункт 3 закрывает единственное место, где данные исчезают
безвозвратно и без предупреждения: база и блобы не попадают ни в один
бэкап. Пункт 2 закрывает разрывы конвейера, которые сервер замечает, но
чинить их сегодня приходится руками.

## 10. Человеческий чек-лист (§22.11)

Только то, что нельзя сделать из репозитория. Порядок — по тому, что
разблокирует больше всего работы.

### Решения владельца

1. **Branch protection.** Приватный репозиторий на плане Free не даёт ни
   protection, ни rulesets. Выбрать: GitHub Pro, сделать репозиторий
   публичным (нельзя: в истории личные данные), либо принять PR-режим без
   технического запрета на push в `main`. До решения §17.6 п. 1 закрыт
   быть не может.
2. **Логин Codex** на BetaPi: `codex login`. Без него независимого ревью
   §14.1 не существует, и ни один PR с моделью данных, миграцией,
   безопасностью или рекордером формально не может быть смержен.
3. **Порядок P0.** Подтвердить предложенную последовательность PR из
   раздела 4 или переставить.
