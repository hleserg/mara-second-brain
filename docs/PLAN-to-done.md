## 0. Контекст: почему план именно такой

Владелец попросил один документ, который ведёт от «сегодня» к
«доделано, развёрнуто, проверено», с отдельно собранными в мешки задачами,
где нужен он сам.

Разведка перед составлением плана дала один решающий факт:

**Код ушёл далеко вперёд развёртывания и потока данных.**

| Что мерил | Команда | Значение |
|---|---|---|
| Тестов на `main` | загрузчик unittest, `4abd91d` | 427; после #82 на `0ca51cb` — 436 |
| Самопроверок | `run-tests.sh` → `grep -c "^ok  "` | 29 |
| Отставание doctor | `git rev-list --count HEAD..origin/main` | 51 коммит |
| Событий в реестре | `select count(*) from events` | 2 |
| Звонков за 7 дней | тот же реестр | 1 |
| Заметок в волте | `find /srv/vault -name '*.md' \| wc -l` | 1667 |
| Записей в журнале решений | `grep -c '^## ' docs/decisions.md` | 86 |
| Файлов ADR | `ls docs/adr/` | 9 (из 12 обязательных); 12 после Т9.2 (2026-10-05) |
| Открытых issue / PR | `gh issue list` / `gh pr list` | 5 / 2 |

При этом `tdlib-ingest` на doctor **выключен**, у Gmail **нет OAuth-клиента**
(крон печатает «нет входа: нет GMAIL_CLIENT_ID»), телефон последний раз
присылал данные **2026-09-07**, `heartbeat`-файлов нет ни одного.

Отсюда форма плана: **сначала оживить поток данных (это почти целиком
мешок владельца), потом закрывать инженерию.** Писать Control Plane над
реестром, в котором два события, — строить панель над пустотой; §22.7 это
прямо запрещает («не строить Control Plane поверх нестабильной authority
model»), §22.8 запрещает новые коннекторы до закрытия рисков тихой потери.

**Два возможных финала, оба честные (§23):**

* **autonomous reliable memory capture** — если после перезагрузки телефона
  запись стартует сама и полевая матрица R01–R14 это подтверждает;
* **degraded prototype with monitored recovery** — если не стартует, но
  система это честно видит, кричит в измеренный срок и восстанавливается по
  воспроизводимой инструкции.

Второй финал — не провал и не подлежит маскировке под первый (§7, §17.2).
Какой из двух — решает мешок М4, не код.

## 1. Как читать и как вести этот план

1. **Два уровня.** Здесь — волны и карточки задач (цель / §ТЗ / файлы /
   критерий / размер / зависимости / кто). Пошаговые TDD-шаги пишутся в
   момент старта задачи. Не ищи их здесь и не считай их отсутствие пробелом.
2. **План самообновляемый.** PR, закрывающий пункт плана, **в том же PR**
   ставит галочку в этом файле. Issue #39 сгнил за шесть дней ровно потому,
   что этого правила не было. Закрытая волна — это ещё и обновлённая
   таблица §7 в `docs/current-state-audit.md` в том же PR (§22.14), а не
   только отметка в Т9.6.
3. **Размеры:** S ≈ один PR за присест, M ≈ один PR за день, L ≈ несколько
   PR подряд.
4. **«Кто»:** `агент` — делаю сам без вопросов; `владелец` — в мешке;
   `агент+гейт` — делаю сам, но выполняю только после явного разрешения.
5. **Числа — это утверждения.** Любое число в этом плане получено командой,
   и команда названа. Новое число не пишется без счёта (правило 16).
   Имя документа и номер строки — тоже утверждение про конкретное дерево;
   дерево называется (правило 20).

## 4. Гейты и правила, действующие на весь план

**Г1. Гейт тестов.** `mkdir -p ~/.mara-tmp && TMPDIR=~/.mara-tmp
SKIP_ANDROID=1 bash scripts/run-tests.sh`. `mkdir -p` не украшение:
`run-tests.sh` делает песочницу через `mktemp -d "${TMPDIR:-/tmp}/…"`, а
`mktemp` не создаёт отсутствующий родительский каталог и падает с rc=1 до
первого теста — проверено на несуществующем `TMPDIR`. Число тестов ловится `grep -E "^Ran |^OK"`,
самопроверки — `rtk proxy grep -c "^ok  "`. `tail -N` обрезает строку `Ran` —
не пользоваться им для счёта.

**Г2. Гейт Kotlin.** Локального JDK нет. Проверка — либо job `kotlin` в CI,
либо `ssh doctor` + gradle. Kotlin-правка без одного из двух не считается
проверенной.

**Г3. Гейт мерджа (§14.2а).** CI зелёный + Г1 зелёный **на смерженном
дереве** + ревью пройдено + ≤5 кругов. Никогда не мержить на красном гейте,
при неразрешённом конфликте и при поломке живого потребителя `main`.

**Г4. Гейт опасной миграции (§14.1).** Миграция схемы реестра выполняется на
doctor только когда: doctor на `origin/main` **и** свежий `core-backup.py`
с пройденным учением восстановления **и** явное разрешение владельца.
Разработка — автономна, исполнение — за гейтом.

**Г4 не срабатывает сам, и один раз его уже прошли мимо.** Миграции реестра в
этом коде не отдельная команда: `_ужать_ledger()` зовётся из
`mara_ingest.connect()` и перестраивает `commitments`, `conversations`,
`projections`. Проверка схемы (`pragma table_info`) идёт при каждом открытии
базы, сама перестройка — один раз: дальше функция выходит сразу. Значит выкат
кода, который её содержит, **и есть** миграция — а выглядит как обычный `reset --hard`. Выкат
2026-09-11 нёс `e55dfc8` (PR #79) и выполнил перестройку рестартом демона, без
разрешения и без учения восстановления. Урон нулевой и это проверено: во всех
трёх таблицах 0 строк, `*_old` не осталось. Защита теперь в шаге 2
`docs/RUNBOOK-deploy.md`: диапазон проверяется на `connect`/`_ужать_ledger`
до сброса дерева. Учение Т3б.1 из «хорошо бы» стало предусловием следующего
такого выката.

**Г5. Гейт выката — снят 2026-09-11.** Владелец передал выкат на doctor мне
(«разрешил», ответ на М5 п.1). Выкатываю сам: `main` на doctor,
`install-cron.sh --check` → `--apply`, рестарт `contextd`, оживление TDLib и
Gmail в той части, где не нужен его браузер. **Гейт Г4 это не отменяет**:
миграция схемы реестра (Т2.8) по-прежнему требует отдельного разрешения,
свежей копии и пройденного учения восстановления.

**Г6. Секреты.** Ключ не присваивается переменной bash, не идёт в
командную строку и не пишется в heredoc: любая ошибка печатает его целиком.
Читать и писать ключи — питоном на целевой машине, проверять косвенно.

**Г7. Публичность.** Перед каждым коммитом в публичный репозиторий —
проверка на домашние адреса, системные имена пользователей, имя владельца,
номера телефонов, названия личных папок.

## 8. Проверка целиком (как понять, что готово)

**Уровень 1 — гейт.** Г1 зелёный, CI зелёный, счёт тестов растёт и назван.

доказательством. Пункты, требующие поля, закрываются полем.

**Уровень 3 — цикл §23.** Один непрерывный прогон:

```
перезагрузка телефона → здоровье не врёт → обычный звонок → обе стороны
разборчиво → файл однозначно связан со звонком → сеть падает и
возвращается → загрузка завершается ровно один раз → ASR и говорящие дают
проверяемые сегменты → обязательство извлечено с правильными
owner/requester/срок → evidence открывает нужный фрагмент → владелец
правит и закрывает → ревизия и аудит без потерянного обновления → новый
пак немедленно вытесняет старый → Claude, Codex, Hermes и PWA видят одно
состояние → бэкап восстанавливает реестр и блобы, Markdown пересобирается
```

Вердикт записывается в `docs/current-state-audit.md` одним из двух слов:
**autonomous reliable memory capture** или **degraded prototype with
monitored recovery**. Второе — не провал, но и не маскируется под первое.
